# 从 App 入口到可调用能力：AI 时代的产品设计变化

AI 时代的变化，不只是多了一个聊天框。更深的变化是：用户可以先说自己想完成什么，再由系统寻找合适的软件能力并安排步骤。

过去，软件通常等待用户打开 App、进入页面、找到功能。新的设计思路则要求软件把自己的能力描述清楚，让人或 AI 都能找到并调用。Apple 的 App Intents 是这类思路的一个平台实现；本文关注的是更广泛的产品设计影响，而不是某个框架的使用方法。

```text
用户表达目标 → 系统选择能力 → 软件执行动作 → 用户检查结果
```

## 一、交互起点从“选功能”变成“说目标”

传统交互要求用户知道工具在哪里、功能叫什么、操作顺序是什么。用户要约一场会议，可能需要打开日历、查看空闲时间、切到聊天软件联系同事，再返回日历创建活动。

目标驱动的交互允许用户直接说：“找一个大家下周都空的时间，建一个会议，并发消息确认。”系统负责把请求拆成查日历、确认参与者、创建活动和发送消息等步骤。

这会把一部分操作负担从用户转到系统。不过，用户表达目标并不意味着系统应该不经检查地完成所有步骤。遇到信息缺失、对象不明确或风险较高的操作，系统仍需要追问或请求确认。

## 二、UI 从功能目录扩展为任务中的控制界面

如果用户可以直接描述目标，App 首页就不必总是唯一的入口。简单任务可能从搜索框、语音或系统建议开始；系统也可能在当前页面提供针对眼前内容的操作。

但自然语言并不适合所有事。浏览照片、比较机票、剪辑视频时，图像、表格和时间轴通常比对话更容易检查和控制。因此，未来的 UI 更可能按任务分工：

- 简单、重复的操作可以直接调用。
- 缺少关键信息时，界面用一个具体问题补全信息。
- 涉及付款、发送、删除等操作时，展示内容并要求确认。
- 需要浏览、比较或精细编辑时，打开完整工作界面。

这意味着 UI 的设计问题会从“怎样把功能排进菜单”扩展为“任务进行到哪一步，用户现在需要看见什么、决定什么”。有些界面可能成为短暂的任务面板；复杂任务仍需要完整的 App 页面。

## 三、Feature 不会消失，但会从菜单项变成能力

Feature 仍然是软件提供的价值。变化的是用户是否需要知道它的名字、位置和使用步骤。

例如，“收藏”这个 Feature 仍存在。过去，用户可能需要找到收藏按钮；现在可以表达：“把这篇文章放进我周末要读的清单。”用户描述目标，系统找到收藏动作，并补上目标清单这个参数。

可以从三个层面理解 Feature 的变化：

1. **用户层**：Feature 不一定以按钮或菜单项出现。用户说目标，系统寻找适合的功能。
2. **系统层**：Feature 需要成为边界明确、可以调用的能力，包含输入、权限和结果。
3. **产品团队层**：Feature 仍是规划和开发单位，团队仍要判断它服务谁、解决什么问题、怎样衡量效果。

因此，需求可能从“增加收藏按钮”变成“让用户能保存内容，并在之后找回、整理和继续处理”。前者关注界面元素，后者关注完整能力。

## 四、API 从“能调用”走向“能被理解和组合”

传统 API 可以告诉程序怎样传参数，但 AI 还需要理解动作对用户意味着什么。一个适合被系统调用的能力，至少要说明：

- 动作会做什么；
- 需要哪些输入；
- 输入所指的对象如何识别；
- 执行成功会返回什么；
- 会不会修改数据、影响他人或产生费用；
- 失败后能否安全重试，是否可以撤销。

例如，“处理订单”范围太宽，系统难以判断它会查订单、改地址还是退款。把它拆成“查询订单”“修改配送地址”“申请退款”等动作，更容易解释，也更容易在用户确认后组合使用。

但动作不能拆得无限细。动作太粗，副作用难以预测；动作太碎，系统会面对过多选项，组合也更困难。好的能力边界需要同时便于用户理解、系统选择和团队维护。

**设计推测：** API 的描述质量会越来越直接地影响产品体验。描述不清的能力，可能让助手选错工具、问错问题或无法解释结果。接口因此不仅是工程连接，也会成为产品可发现性的一部分。

## 五、跨 App 工作流要求能力和数据可以交接

很多目标跨越不止一个 App。安排旅行可能要查日历、搜索交通、预订住宿、保存确认信息。系统要完成这类任务，需要各个服务提供可组合的能力，也需要把一个 App 的结果安全地交给下一个 App。

这类能力在不同平台上会通过不同机制提供。Apple App Intents、Android Assistant Actions、网页 API 和 AI 工具协议并不是同一个标准，但都在处理相近的问题：系统如何发现功能、传入正确的信息、调用软件并接收结果。[Apple App Intents](https://developer.apple.com/documentation/appintents/app-intents) · [Android App Actions](https://developer.android.com/develop/devices/assistant/get-started) · [MCP Tools](https://modelcontextprotocol.io/specification)

对产品架构来说，一个可行方向是把核心业务能力放在稳定的服务层，再为不同平台和助手提供适配接口。这样可以复用业务规则，同时按平台处理身份验证、参数格式和交互确认。

## 六、权限和确认成为能力本身的一部分

用户在页面里点按钮时，通常知道自己正处于哪个 App、将执行什么操作。助手代为调用后，这些信息可能不再那么明显。

因此，产品需要区分查询、修改、发送、付款和删除等不同影响，并明确规定哪些可以自动执行、哪些需要确认。用户还需要看到实际结果，知道任务是否完成，以及操作能否撤销。

Apple 当前面向智能体功能的开发者资料讨论了高风险操作的情境化确认和设备解锁要求。这反映出一个普遍的设计原则：安全不能只依赖模型“理解要谨慎”，还要由权限、验证和运行时规则落实。[Apple：防范智能体功能风险](https://developer.apple.com/videos/play/wwdc2026/347/)

## 七、产品竞争可能转向“谁能被可靠地调用”

过去，App 主要通过桌面图标、应用商店搜索、广告和用户习惯获得入口。如果用户先向 AI 助手表达目标，助手可能替用户选择服务、排序选项并执行操作。

**设计推测：** 这会让服务的可发现性、可靠性、价格透明度和用户授权变得更重要。AI 助手和操作系统也可能因为控制推荐与调用顺序而成为新的分发入口。某个 App 可能继续提供服务，但用户未必每次都看到它的品牌或界面。

这不表示界面和品牌失去意义。用户仍会主动浏览内容、比较产品、参与社区，也会在复杂或重要任务中进入完整 App。变化是：产品既要服务直接使用界面的人，也要让系统知道何时适合调用它。

## 八、并非所有任务都应该交给 AI

自然语言适合表达目标，却可能含糊；AI 可能误认对象、遗漏条件或遇到无法执行的步骤。对于低风险的重复任务，自动完成可以减少操作；对于复杂或高风险的任务，系统可能更适合先整理信息，再让用户决定。

所以，好的设计不是把每个页面换成聊天框，而是让用户在对话、按钮、浏览和完整界面之间自然切换。用户应能知道系统做了什么、修改结果、补充信息，并在必要时撤销操作。

## 结语：软件要同时面向人和系统

App 不只是页面，Feature 也不只是按钮。它们都代表软件提供的能力。AI 让这些能力更可能脱离原有页面，被系统按用户目标发现、组合和调用。

**更准确的判断是：软件正在从“以页面和功能菜单为中心”，扩展为“同时以用户目标和可调用能力为中心”。** App Intents 是这种变化的一个例子；更广泛的影响会落在 UI 组织、Feature 边界、API 设计、权限规则和产品分发上。
