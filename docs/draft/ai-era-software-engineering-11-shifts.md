# AI 时代的软件工程：11 个正在发生的变化

AI 正在改变软件开发，但真正重要的变化，并不是它能写出多少代码，而是代码生产成本下降之后，软件工程的瓶颈将转移到哪里。

过去，软件开发往往受制于工程师的编码能力、开发时间和团队协作效率。随着 AI 编程能力提升，越来越多的实现工作可以交给 AI 完成。然而，需求是否正确、系统设计是否合理、缺陷能否被发现、变更是否安全，以及软件能否在生产环境中稳定运行，并不会因为代码生成变快而自动解决。

因此，与其断言代码审查、单元测试或敏捷开发即将消失，不如更准确地讨论：AI 将如何改变这些实践的目的、成本和执行方式。

## 1. 代码审查将从逐行阅读，转向变更与风险审查

AI 可以在很短时间内生成大量代码。如果每次修改都要求工程师逐行阅读、理解每个函数，再逐一检查其正确性，人工审查很容易成为开发流程的瓶颈。

例如，一个 AI Agent 接到“修复登录接口在并发请求下偶发失败”的任务，可以定位相关代码、修改锁机制或事务处理逻辑、补充回归测试并提交 Pull Request。此时，审查者真正需要回答的，不只是每行代码是否写得漂亮，而是：

- 是否修复了真正的并发问题？
- 是否引入死锁、性能退化或新的竞争条件？
- 是否改变了认证、授权或事务边界？
- 是否有测试证据证明旧问题已经解决？

但代码审查不会因此失去价值。架构合理的系统，仍然可能因为一条 SQL 查询遗漏租户过滤条件而产生严重安全问题。代码审查还承担风险控制、变更追溯和责任确认等职责。

未来更可能出现的模式是：AI 对大量变更进行初筛，自动化检查验证可机械化的规则，人类重点审查业务语义、系统边界、高风险变更和无法自动证明的决策。

**结论：人工逐行阅读所有代码的模式可能弱化，但以变更意图、风险和验证证据为中心的代码审查会继续存在。**

## 2. 单元测试不会消失，但测试策略将重新设计

一种常见的预测是：AI 可以随时重写整个实现，因此逐个代码单元进行测试没有意义，未来只需要接口测试、集成测试和系统测试。

这个推理忽略了单元测试的核心价值。单元测试并不是为了永久保护某段实现，而是为了快速验证局部行为是否符合约定。

例如，订单金额计算逻辑需要保证折扣计算正确、退款金额不超过已支付金额、货币舍入符合业务规则，且边界输入不会导致错误。即使 AI 明天彻底重写这个函数，这些约束依然存在，测试仍然可以验证它们。

当然，AI 时代确实值得清理低价值测试，例如只验证简单 getter/setter 的测试、依赖内部实现细节的测试，以及维护成本高却没有保护重要行为的重复测试。

测试策略应更多围绕业务不变量、边界条件和可观察行为展开，并结合单元测试、契约测试、集成测试和端到端测试。端到端测试也不是万能的：它通常更慢，问题定位更困难，也难以覆盖所有输入。

**结论：单元测试不会普遍消失；依赖实现细节的测试可能减少，而验证业务行为和关键约束的测试会更重要。**

## 3. 软件开发的竞争力将从编码产出，转向问题定义与交付能力

AI 能够承担越来越多的实现工作，但软件交付仍然需要理解业务问题、定义行为、管理依赖、部署系统、处理异常并验证结果。

以开发一个 Jenkins 故障分析 Agent 为例。过去，工程师可能需要手动编写 Jenkins API 调用、构建日志解析器、失败分类逻辑、GitHub 提交记录关联和 Teams 通知功能。现在，AI 可以承担大量初始实现工作。

工程师的关键任务则可能转向：

1. 明确需要监控哪些 Jenkins 实例和流水线。
2. 定义失败分类标准，以及何时必须升级给人工。
3. 设计凭证权限和数据访问边界。
4. 设定准确率、误报率和平均恢复时间等指标。
5. 在真实流水线上验证效果，并处理误判。

这些工作并不比编码次要。代码生成得再快，也不能自动证明它解决了正确的问题。

这不意味着开发者不再需要理解代码。面对性能瓶颈、分布式系统故障、内存泄漏或安全漏洞时，理解实现依然是诊断问题的重要能力。

**结论：软件开发的价值重心将从手工生产代码，转向定义问题、设计约束、编排 AI、验证实现、控制发布风险，以及持续改善生产系统。**

## 4. 需求与规格缺陷将成为更突出的质量风险

AI 可以减少一部分常见实现错误的修复成本，但这不代表其他类型的 Bug 会消失。需求缺陷、规格缺陷、实现缺陷、集成缺陷、安全缺陷和运行时缺陷仍然可能同时存在。

假设需求规定：“用户可以取消尚未发货的订单。”AI 可能生成完全符合文字描述的代码，但实际系统中，订单服务检查状态的同时，仓储服务可能已经开始发货；两个请求并发执行，也可能导致订单已发货却仍被取消。

这不是单纯的需求表达问题，而是并发、事务和跨服务一致性问题。

反过来，如果业务方没有定义“取消成功但物流已经启动时如何处理”，即使代码没有实现错误，系统仍可能不符合业务预期。

AI 能够帮助发现规格中的歧义，也可以生成测试来验证明确的规则，但它不能凭空决定业务应该采用哪一种政策。

**结论：需求和规格缺陷的重要性可能上升，但它们不会取代实现、集成、安全和运行时问题。未来需要更清晰的业务规则、接口契约、状态转换和验收标准。**

## 5. 开源仍然能够提升质量，但优势不只在于公开源码

“只要关注的人足够多，所有 Bug 都能被发现”从来都不是可靠保证。开源的质量收益也不只是更多人阅读代码。

开源生态还能带来不同环境下的真实使用反馈、独立维护者的设计审查、跨平台兼容性测试、安全研究、可复现的缺陷报告，以及用户提交的补丁和经验。

例如，操作系统内核、数据库和网络基础设施中的缺陷，往往与并发语义、硬件行为、兼容性或长期运行条件有关。AI 可以协助审查补丁，但外部维护者可能凭借特定平台经验或真实负载下的故障报告，发现自动审查没有识别的问题。

AI 也可能基于错误假设生成看似合理的审查结论。多个 AI Agent 同时审查代码，并不自动等于多个真正独立的验证来源。

**结论：AI 降低了代码分析和缺陷筛查的成本，但开源仍能通过独立审查、真实使用和生态协作提升质量。未来，透明的测试、可复现构建、独立验证和持续维护可能比单纯公开源码更重要。**

## 6. 敏捷不会死亡，人工协调型流程将被重新设计

AI 生成代码的速度，不等于整个项目的交付速度。

软件交付还包括需求澄清、依赖协调、测试、评审、用户验收、发布和生产问题处理。AI 可以加快其中一些环节，却无法自动消除所有外部依赖。

例如，AI 可能在半小时内生成支付接口、前端页面、数据库迁移和测试代码，但项目仍然需要配置支付服务商环境、验证幂等性和退款规则、制定数据迁移与回滚策略，并完成灰度发布和生产验收。

敏捷的核心价值也不只是每日站会或固定长度的 Sprint，而是通过小批量交付、快速反馈和持续调整，降低做错产品的概率。

AI 甚至可能让反馈机制更加重要：团队可以更快构建原型、收集用户意见，再调整需求，而不是在一开始就试图预测所有需求。

传统 Scrum 中的一些仪式可能会简化。一个人管理多个 AI Agent 的小型项目，未必需要复杂的角色分工和大量状态同步会议。但任务拆分、优先级管理和反馈闭环仍然有价值。

**结论：传统敏捷流程中的部分仪式和人工协调成本会下降，但小批量变更、快速反馈和持续交付不会因此失去意义。**

## 7. 固定的角色边界将弱化，个人的执行能力将扩大

传统软件项目通常由项目经理、设计师和工程师承担不同职责。AI 正在降低这些职能之间的执行门槛，让一个人有机会完成过去需要多个专业人员协作的工作。

例如，一个 DevOps 工程师可以借助 AI 分析现有 Jenkins 流水线和故障记录、设计 API 与数据模型、生成管理界面、编写后端服务和自动化测试，再将系统部署到测试环境并生成使用文档。

但个人执行能力扩大，不等于专业知识和独立复核不再重要。复杂的用户研究、合规要求、分布式系统设计、安全审计和多团队依赖，仍然可能需要专业人员参与。

一个人可以调用多个 AI Agent，也不代表这些 Agent 就构成了真正独立的专业审查。它们可能共享相似的模型局限、上下文缺失和错误假设。

**结论：项目分工可能从固定职能分工，部分转向按任务动态组合的 AI 协作模式。小型项目中，一个人可以兼任多个角色；大型项目仍需要专业知识、独立审查和明确的责任边界。**

## 8. 好代码的标准将从可读性扩展到可验证性和可演进性

“好代码”的传统标准包括可读性、可测试性、可重构性和可维护性。这些标准并不只是为了方便人类阅读，也关系到故障隔离、运行效率、系统演进和自动化工具的可靠性。

假设有两个功能相同的服务：

- 实现 A 是一个巨大的函数，把业务规则、数据库操作、网络请求和异常处理混在一起。
- 实现 B 将业务逻辑、数据访问和外部接口清晰分离，并明确关键不变量。

两者在简单测试中可能表现一致，但当需要修改退款策略、替换数据库或排查生产故障时，B 通常更容易定位变更范围，也更容易编写针对性测试。

AI 可以尝试重构 A，但重构过程本身仍然有风险。清晰的模块边界能够降低这种风险，也能帮助 AI 理解代码、定位依赖并安全修改。

另一方面，传统质量标准也值得调整。过度追求抽象、为了复用而引入复杂设计，可能比简单、隔离良好的实现更糟糕。

**结论：好代码的概念不会消失，但评价标准会扩展到可验证性、模块边界、可观测性、安全性、变更成本，以及 AI 能否可靠地理解和修改代码。**

## 9. 代码规范将更多由机器执行，而不是依靠人工遵守

AI 不需要主动“在乎”代码风格。只要自动化管道能够强制执行规则，规范就可以持续发挥作用。

在大型 TypeScript 项目中，如果不同 Agent 采用不同的命名方式、导入顺序、错误处理模式和类型约定，代码库可能迅速变得难以维护。

通过 ESLint、Prettier、TypeScript strict mode 和 CI 检查，团队可以自动发现或拒绝不符合约定的代码、类型错误、部分可疑控制流和违反项目约定的实现。

AI 生成的代码越多，这类低成本、可重复执行的质量门槛反而越有价值。

不过，不是所有规范都值得机械保留。比如，为了满足固定行宽而拆分表达式，可能降低可读性；过于严格的规则也可能产生噪声。

**结论：Formatter、Linter、类型检查和静态分析不会失去意义。未来应把可机械化的规则交给工具执行，减少人工争论，将注意力集中在架构、行为和风险上。**

## 10. UI 将从固定页面，演变为固定界面与动态交互并存

AI 时代的 UI 变化包含两个不同趋势。

首先，面向 AI Agent 的软件会更加重视 API、结构化参数、机器可读错误、认证授权和幂等性。一个 Jenkins 服务可以提供 `list_failed_builds`、`get_build_logs`、`retry_build` 和 `create_incident_report` 等能力，让 Agent 直接调用，而不必模拟人类点击网页。

其次，面向人的界面可能越来越动态。用户只需提出需求：“比较最近 30 天所有 Jenkins 实例的失败率，按团队分组，并找出失败次数增长最快的 10 条流水线。”AI 就可以生成包含折线图、排序表格和异常说明的专用视图，而不必让用户逐层打开菜单、选择日期和配置过滤器。

但动态 UI 不会取代所有固定界面。高频操作通常需要稳定、可预测的交互；键盘操作、屏幕阅读器和其他可访问性要求依然存在；涉及生产重启、回滚或权限变更时，明确的审批和审计入口可能非常重要。

**结论：面向 AI 的系统会更加重视 API 与机器可读契约；面向人的系统会减少不必要的导航和配置步骤，但仍需要可预测、可访问、安全且可信的交互方式。真正可能变得不重要的，是那些仅仅因为软件无法理解用户意图而存在的繁琐操作。**

## 11. Token 不再只是消耗品，而是需要优化的推理预算

更多 Token、更大的上下文窗口和更多推理计算，确实可能帮助模型处理复杂任务。但 Token 消耗量不等于软件质量，投入更多 Token 也不保证得到更好的系统。

最终效果至少取决于四类因素：

1. **模型能力**：模型能否正确理解需求、推理并生成实现。
2. **上下文质量**：需求、代码库信息、架构约束和历史决策是否准确。
3. **推理与验证预算**：是否有足够资源探索方案、运行测试、分析错误并迭代。
4. **工程环境**：是否能够访问真实依赖、测试环境、日志、监控和部署系统。

假设两个团队开发同一个功能。团队 A 有很高的 Token 预算，但需求模糊、测试环境不完整，且主要依赖 AI 自我评价；团队 B 使用中等预算，却有明确的验收标准、完整的集成测试和清晰的权限边界。团队 A 可能生成更多代码、尝试更多方案，但团队 B 仍然可能更快交付可靠的实现。

在复杂系统分析、跨模块重构或困难的故障诊断中，更强的模型和更高的推理预算可能带来显著收益。但当瓶颈是需求不清、测试缺失或环境不可用时，单纯增加 Token 的收益会很有限。

成本也不只有 Token：延迟、工具调用费用、测试环境资源、人工审核时间和生产故障风险，都需要纳入考虑。

**结论：推理预算、模型能力和上下文资源将成为重要生产要素，但不是唯一决定因素。真正有竞争力的团队，是能够把模型资源转化为经过验证的业务价值的团队，而不是单纯消耗最多 Token 的团队。**

## 现实证据：生成更快，不代表交付必然更好

Google Cloud 的 DORA 2024 研究显示，AI 采用与部分开发者生产力和代码质量指标的改善相关，但研究也报告了与交付稳定性下降相关的结果。这提醒我们：代码生成速度、代码质量和整体交付表现是不同的指标。

一种可能的解释是，AI 让开发者更快地产生代码，却也可能导致更大的变更批次。如果测试、审查和发布流程没有同步改善，整个交付系统仍然可能变得不稳定。

这不能证明所有团队都会出现相同结果，也不能单凭相关性确定因果关系，但它反驳了一个过于简单的假设：只要 AI 足够快，项目交付就会自然变快。

参考资料：

- [Google Cloud：Announcing the 2024 DORA Report](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)
- [DORA Research](https://dora.dev/research/)

## 结语：软件工程不会消失，稀缺能力正在转移

AI 不会让软件工程消失，而是会让“生产代码”从核心稀缺能力，逐渐变成一种相对廉价的能力。

真正稀缺的东西将更可能是：

- 判断什么问题值得解决。
- 把模糊需求变成可验证的规格。
- 设计能够安全演进的系统。
- 识别 AI 自身无法可靠发现的错误。
- 将生成的代码转化为稳定、可维护、可持续交付的软件。

未来的软件工程师可能不再以写了多少行代码、完成了多少个函数来衡量价值，而更需要关注：**解决了什么问题、交付了什么结果，以及这个结果是否经得起验证。**

这才是 AI 带来的真正范式变化。代码审查、单元测试、敏捷流程、代码规范和 UI 不一定会消失，但它们的执行方式、成本结构和价值重点都会发生变化。

AI 可以让实现变得更便宜、更快，却不会自动让正确性、可靠性和业务价值变得廉价。
