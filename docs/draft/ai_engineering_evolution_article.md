# 从 Prompt Engineering 到 Agentic Engineering：AI 工程方法论的演进

## 1. 从"让 AI 回答"到"让 AI 完成工作"

Carlo 是一位意大利人。你猜他喜欢什么 Pizza？

AI 可能回答 Margherita：它是经典的意大利
Pizza。不过，这只是根据一般知识作出的推测。Carlo 也许更喜欢
Pepperoni，或者根本不喜欢 Pizza。

如果我们希望 AI 不只是猜一个答案，而是知道 Carlo
的真实偏好、查找符合条件的菜单、控制预算、检查配料，最后在获得授权后完成订购，那么问题就变了。

我们不再只关心"怎样让 AI 给出更好的答案"，还要考虑：

-   它是否理解任务？
-   它能否取得正确的信息？
-   它是否知道什么才算成功？
-   它能否调用真实工具采取行动？
-   它的行动是否受到权限约束？
-   失败后能否根据反馈调整？
-   最终结果能否被独立验证？

这也正是 DevOps 中正在发生的变化。以前，工程师把 Jenkins
的失败日志复制给 AI，要求它解释错误；现在，AI Agent
可能读取日志、检查代码、修改文件、运行测试，并在权限允许的范围内继续处理故障。

本文用两个场景贯穿这段演进：

-   **Pizza 场景：** 从猜 Carlo 喜欢什么，到可靠地为他安排晚餐。
-   **DevOps 场景：** 从解释 Jenkins
    日志，到受控地诊断、修复和验证故障。

需要先说明：本文所讨论的概念并不是严格按年份依次出现、彼此替代的八个世代。很多思想早有研究和工程实践；随着模型能力和工具生态变化，它们逐渐组合成更完整的系统方法。

## 2. Prompt Engineering：把模糊要求变成清晰指令

Prompt
Engineering（提示词工程）关注的是：如何设计指令，让模型更准确地理解任务，并生成符合要求的输出。

最初的问题是：

> Carlo 是意大利人。你猜他喜欢什么 Pizza？

改进后的提示词可以是：

> 请猜测 Carlo 最可能喜欢哪种
> Pizza，给出理由，并明确区分推测与事实。仅凭国籍不能确定他的个人口味。

AI 可能回答：

> 我猜他可能喜欢 Margherita，因为它是经典的意大利
> Pizza。但这只是推测；仅凭国籍无法判断 Carlo 的真实偏好。

这就是提示词工程的价值：明确任务、限定输出、提醒模型表达不确定性。

### 当时令人眼前一亮的技术：结构化 Prompt、Few-shot 和思维链提示

早期提示词实践中，一个明显进步是从随意提问转向有结构的指令，例如：

``` text
角色：你是一名 DevOps 故障分析助手。

任务：分析 Jenkins Pipeline 失败日志。

输入：
- 构建日志
- 最近一次代码变更
- 相关测试结果

要求：
1. 找出第一个有诊断价值的错误。
2. 区分日志中确认的事实与推测。
3. 按可能性排序给出根因。
4. 为每个根因提出验证方法。
5. 不要把未经验证的假设说成事实。

输出：
- 关键证据
- 候选根因
- 验证步骤
- 当前不确定性
```

结构化 Prompt 让任务、上下文、约束和输出格式更清晰。Few-shot prompting
则通过提供少量示例，让模型模仿预期的回答方式。

另一项令人眼前一亮的进展是 **Chain-of-Thought（CoT，思维链）提示**。2022
年的相关研究展示了通过示例引导模型生成中间推理步骤，能够改善某些多步推理任务的表现。随后，ReAct
等研究进一步探索如何把推理与行动交替结合起来。

例如，面对 Jenkins
错误，模型可以先区分"依赖下载失败"和"测试断言失败"这两种可能性，再根据日志判断下一步该检查什么，而不是立刻给出一个未经证实的结论。

这里需要区分：思维链提示是一种引导推理的技术，不代表模型展示出来的每一步推理都一定正确，也不意味着生产系统必须暴露模型的完整内部推理。实际系统更应输出可检查的依据、决策摘要和验证结果。

### 边界在哪里？

如果我们只知道 Carlo 是意大利人，即使提示词再精巧，也无法知道他最喜欢的
Pizza 究竟是什么。

同样，如果 Jenkins 日志只有：

``` text
ERROR: Build failed
```

模型也无法可靠地判断根因。

**Prompt Engineering 改善的是指令表达，不会自动补齐缺失的事实。**

## 3. Context Engineering：先把正确的信息摆上桌

Context
Engineering（上下文工程）关注的是：如何为模型选择、组织、检索和更新完成任务所需的信息。

假设 AI 现在可以访问 Carlo 的偏好资料：

``` yaml
person: Carlo
favorite_pizza: Pepperoni
dislikes:
  - olives
usual_takeaway_day: Friday
budget_eur: 20
```

再问：

> Carlo 最喜欢什么 Pizza？他通常什么时候点外卖？有什么配料需要避免？

AI 现在可以依据资料回答：Carlo 最喜欢
Pepperoni，通常星期五点外卖，并且不喜欢橄榄。

这次回答不再只是根据国籍作出的猜测，而是基于相关资料。

真实系统中的上下文可能来自用户资料、对话历史、知识库、代码仓库、构建日志、测试报告、数据库和外部
API。关键不只是"塞入更多资料"，而是确保资料相关、可信、及时，并在需要时被正确检索。

### 当时令人眼前一亮的技术：RAG、长上下文、向量检索与记忆

**Retrieval-Augmented Generation（RAG，检索增强生成）**
将检索到的资料提供给模型，让它基于外部内容回答问题。向量数据库和语义检索则帮助系统从大量文档中找到语义相关的内容。

在 Pizza 场景中，系统可以从 Carlo 的个人偏好记录中检索到"不吃橄榄"；在
DevOps 场景中，可以从历史故障记录中找出与当前错误相似的案例。

长上下文窗口让模型一次处理更多资料，但上下文越长并不必然越好：无关信息、过时资料和互相矛盾的记录仍可能降低质量。上下文工程因此还包括信息筛选、排序、压缩、来源追踪和状态管理。

**Prompt 决定怎样问；Context 决定模型回答时能看到什么。**

## 4. Spec-Driven Development：先定义什么才算成功

有了资料，AI 就一定能完成任务吗？还不够。

"帮 Carlo 选一款好吃的
Pizza"仍然很模糊。最受欢迎的款式未必符合他的口味；价格最低的也未必合适。

我们需要把目标转化成可以检查的规格：

``` yaml
task: choose_friday_pizza

requirements:
  must_be_pizza: true
  preferred_topping: Pepperoni
  forbidden_ingredients:
    - olives
  maximum_total_price_eur: 20

acceptance_criteria:
  - item_is_a_pizza
  - olives_are_absent
  - total_including_fees_is_at_most_20_eur
  - ingredients_and_price_are_verified
```

这里，Pepperoni 是偏好；不能含橄榄和总价不超过 €20
则是硬性约束。如果没有满足条件的商品，AI
应该报告问题，而不是假装找到了合适选项。

### 当时令人眼前一亮的技术：结构化输出、JSON Schema、测试先行与规格驱动工作流

结构化输出让模型按照指定的 JSON Schema
或其他数据结构返回结果，减少下游系统解析自由文本时的歧义。测试先行、验收测试和规格驱动开发，则把"完成任务"的判断转化为可执行的检查。

例如，Agent 可以输出候选 Pizza
的名称、配料、价格、配送费和证据来源；程序再逐项检查硬性条件，而不只是让模型自己宣布"符合要求"。

在 DevOps
中，规格可以规定：修改必须限定在指定范围，不能通过删除测试来制造成功，相关测试必须通过，生产部署需要审批，并且最终报告必须包含验证证据。

规格驱动开发并非 AI
时代才出现的新思想。软件工程早已有需求规格、契约和验收测试。AI
让它们变得更重要，是因为模型可以快速执行大量操作，而模糊目标也可能被快速放大成实际风险。

## 5. Agent Engineering：从给建议到采取行动

到目前为止，AI
可以理解指令、读取资料，也知道验收标准。但它仍可能只会告诉我们该做什么。

Agent
Engineering（智能体工程）关注的是：如何让模型在工具和运行环境支持下，主动执行完成任务所需的步骤。

Carlo 的任务可以变成：

``` text
读取偏好
   ↓
查询菜单
   ↓
检查配料和价格
   ↓
筛选候选项
   ↓
比较并验证
   ↓
提交结果供确认
```

在 DevOps 中，Agent 可以读取 Jenkins
构建记录、检查相关代码、查看最近的提交、提出最小修复方案、修改工作区文件，再运行相关测试。

### 当时令人眼前一亮的技术：Function Calling、ReAct、工具使用与多 Agent

**Function Calling / Tool Calling**
让模型以结构化方式请求程序调用函数或工具。例如，它可以请求查询某个
Jenkins 构建，而不是仅仅写出"请查询 Jenkins"。

ReAct（Reasoning and
Acting）代表了另一项重要思路：让模型交替进行推理、行动和观察。模型先判断需要什么信息，调用工具取得结果，再根据观察决定下一步，而不是仅靠内部知识一次性回答。

随后，各类 Agent 框架将工具调用、状态管理、任务编排和多 Agent
协作组织成可复用的软件结构。

但"能够调用工具"不等于"能够可靠完成任务"。Agent
可能选错工具、误读返回值、修改错误文件，或陷入反复调用。因此，工具执行必须结合权限、反馈和验证机制。

## 6. MCP：让 AI 接入真实世界的工具和数据

当 Agent 数量和外部系统越来越多时，一个新的工程问题出现了：每个 AI
客户端都需要单独集成每一种数据源和工具，开发与维护成本不断增加。

### 令人眼前一亮的技术：Model Context Protocol（MCP）

Anthropic 于 **2024 年 11 月 25 日**公开推出 Model Context
Protocol（MCP）。它提供一种标准化方式，让 AI
应用连接数据源、业务工具和开发环境。可以把它理解为 AI
应用连接外部能力的一种通用接口，而不是一个独立的智能体。

Pizza 场景中，MCP Server
可以暴露餐厅菜单查询、配料信息或订单查询工具。Agent 通过 MCP
客户端使用这些能力，而不必为每一种 AI 应用重新编写一套完全不同的集成。

DevOps 场景中，可以为 GitHub、Jenkins、数据库或内部支持系统提供 MCP
Server，让兼容的 AI 客户端按权限读取构建信息、检索工单或调用指定工具。

MCP
主要解决的是**工具与上下文如何标准化连接**。它本身不会保证模型选对工具，也不会自动为工具调用提供恰当的权限策略、业务流程或验收标准。实际部署仍需要认证、授权、输入校验、审计和风险控制。

## 7. Harness Engineering：给 Agent 一张工牌，也给它一扇门

假设 Carlo 的 AI
已经可以查询菜单、比较价格并准备订单。我们是否应该允许它自动付款？

这取决于授权边界。

一个可靠的系统可以允许 AI
自动读取偏好、搜索菜单和比较价格，但在提交订单或付款之前要求用户确认。

Harness Engineering 关注的是围绕 Agent
建立执行环境、工具接口、权限限制、操作边界和运行约束，使它能够完成任务，同时降低越权或失控的风险。

在 DevOps 中，Agent
可以被允许读取指定仓库、在隔离分支中修改文件并运行测试，但不应因此自动获得生产凭证或部署权限。

### 当时令人眼前一亮的技术：沙箱、权限分层、审批门与可观测性

这里的"眼前一亮"不一定是一项单独的新发明，而是多种成熟工程技术在 Agent
场景中的组合：

-   **Sandbox（沙箱）：** 将执行限制在隔离的工作目录或容器中。
-   **Least Privilege（最小权限）：** 只授予完成任务所必需的权限。
-   **Human-in-the-loop（人在回路）：**
    对付款、生产部署等高风险操作设置确认门。
-   **Audit Log（审计日志）：** 记录工具调用、变更和执行结果。
-   **Policy Enforcement（策略执行）：**
    通过程序化规则限制高风险操作，而不是只靠提示词提醒模型。

提示词可以告诉
Agent"不要部署生产"，但真正的安全边界应由权限和执行环境强制实施。模型可能误解指令，系统控制不能只依赖模型自律。

## 8. Loop Engineering：让系统从失败中调整

第一次搜索到的 Pizza
可能含有橄榄；第二款可能加上配送费后超过预算。可靠的系统不能因为第一次尝试失败，就直接把不合格结果交给
Carlo。

它需要执行、观察、检查、调整，再进行有限的重试。

``` text
执行
  ↓
观察工具结果
  ↓
检查是否满足规格
  ↓
不满足：分析原因并调整
  ↓
有限重试
  ↓
满足要求或停止并请求帮助
```

在 Jenkins 中，Agent
修改配置后运行测试；如果失败，就读取新的日志，判断错误是否与修改相关，再决定是否尝试修正。若多次失败、证据矛盾或风险上升，就应该停止自动执行并请求人工介入。

### 当时令人眼前一亮的技术：反馈循环、状态图与工作流编排

早期 ReAct
等方法已经体现了行动与观察交替的思想。后来，状态图、工作流编排和 Agent
框架让循环、分支、重试、超时和人工审批更容易显式建模。

需要注意，"Loop
Engineering"在本文中是对这类工程实践的概括，并非一个具有统一行业定义、明确起始日期的标准术语。

好的循环不是无限重试。它必须设置最大尝试次数、时间和成本上限，并要求每次重试都利用新的证据。若餐厅明确没有符合条件的商品，反复查询同一菜单不会让合适的
Pizza 凭空出现。

## 9. Evaluation Engineering：别让 Agent 自己给自己打满分

假设 AI 声称："我找到了一款符合要求的 Pepperoni Pizza，总价 €18。"

我们仍然需要验证：菜单是否真的列出该商品？配料是否含橄榄？€18
是否包括配送费？价格信息是否有效？

Evaluation
Engineering（评估工程）关注的是建立系统化、可重复的评估方法，以证据判断模型和
Agent 的实际表现。

### 当时令人眼前一亮的技术：自动评测、回归测试、轨迹评估与可观测性

Pizza 任务可以检查菜单来源、配料、总价和订单状态。Jenkins Agent
则需要验证：

-   相关测试是否真正通过？
-   原先失败的步骤是否成功完成？
-   是否引入回归问题？
-   是否通过删除测试或放宽断言来掩盖故障？
-   Pipeline 是真正完成，还是仅仅启动了重跑？
-   最终结果是否符合任务规格和权限策略？

AI
评测还可以使用固定测试集、已知根因的故障样本、轨迹检查和人工抽查，衡量任务成功率、误报率、错误修改率、重试次数、成本与完成时间。

模型声称"完成"是一项主张，不是证据。测试通过也只能证明测试覆盖到的行为满足了相应检查，不能证明整个系统绝对没有问题。

因此，Evaluation Engineering 需要与执行系统相对独立。不能只让 Agent
自己判断自己做得好不好。

## 10. Skills：不只给工具，还要教 Agent 怎样工作

MCP 可以让 Agent
连接工具，但知道有哪些工具，并不代表知道怎样按照团队流程正确使用它们。

例如，Carlo
的晚餐任务可能有一套固定流程：先检查饮食禁忌，再比较菜单价格，计算配送费，最后将订单摘要交给用户确认。

DevOps
团队也可能有标准化的故障处理流程：先收集日志，再定位首个关键错误，检查最近变更，在隔离分支中修复，运行测试，最后生成证据报告。

### 令人眼前一亮的技术：Agent Skills

Anthropic 于 **2025 年 10 月 16 日**推出 Agent Skills，并于同年 12
月将其发布为开放标准。Skill
通常是一个包含指令、脚本和参考资料的目录，Agent
可以根据任务需要发现并加载它。

一个 DevOps Skill 可以包含：

``` text
jenkins-failure-triage/
├── SKILL.md
├── references/
│   └── common-failure-patterns.md
└── scripts/
    └── collect-build-evidence.py
```

`SKILL.md`
可以说明适用条件、诊断步骤、工具使用规则、输出格式和停止条件；参考资料提供团队内部知识；脚本则可以执行确定性的数据收集或检查。

MCP 与 Skills 的职责不同：

-   **MCP：** 连接外部工具和数据。
-   **Skill：** 封装某类任务的流程知识和操作方法。
-   **Agent：**
    根据当前任务决定何时使用工具、何时加载技能，以及如何推进任务。
-   **Harness：** 控制实际执行权限和边界。
-   **Evaluation：** 检查执行结果是否合格。

因此，可以把 MCP 看作连接能力的接口，把 Skill
看作可复用的工作方法。它们可以组合，但不是彼此替代的技术。

## 11. OpenClaw 与个人 Agent：从聊天窗口走向持续运行的助手

当 Agent 不再局限于开发者 IDE
或单次对话，而是能够连接消息渠道、工具和个人工作环境时，用户开始期待另一种体验：不仅能回答问题，还能持续协助处理任务。

### 令人眼前一亮的技术：OpenClaw 一类的个人 Agent 系统

OpenClaw 的项目历史经历了 Clawd、Moltbot 到 OpenClaw
的更名过程；项目作者在 **2026 年 1 月 29 日**发布 OpenClaw
名称公告。它代表了个人 Agent
的一种实践方向：把模型、消息入口、工具、会话和自动化能力组织在一起，让用户通过日常交互渠道委派任务。

以 Pizza 为例，用户不必每次都打开一个专用网页、重新输入偏好和预算。个人
Agent
可以在授权范围内使用已有上下文，帮助查找选项，并把需要确认的决定交还用户。

在 DevOps 中，类似的 Agent 可以成为日常工作的入口：汇总 Jenkins
失败、检索 GitHub
变更、查询工单、生成初步根因分析，并在授权范围内执行某些重复性操作。

但 OpenClaw 本身并不等同于一种新的工程方法论，也不是所有 Agent
系统都必须采用的架构。它更适合作为一个具体例子，说明 Agent
正从单次问答界面发展为连接工具和工作流的持续助手。

持续运行也会带来新的安全要求：消息渠道身份验证、工具权限、凭证管理、提示词注入防护、审计和人工审批都不可忽略。个人
Agent 越方便、连接能力越强，越需要清晰的安全边界。

## 12. Agentic Engineering：把零件接成可交付的系统

前面讨论的每种方法，都解决了一个重要问题：

-   Prompt Engineering：如何表达任务？
-   Context Engineering：模型能看到什么？
-   Spec-Driven Development：什么才算完成？
-   Agent Engineering：如何采取行动？
-   MCP：如何连接外部工具和数据？
-   Harness Engineering：行动边界在哪里？
-   Loop Engineering：失败后如何调整？
-   Evaluation Engineering：如何验证结果？
-   Skills：如何复用专业流程？
-   OpenClaw 一类系统：如何把 Agent 放进持续的个人或工作场景？

Agentic Engineering
可以理解为围绕这些能力，设计、实现、测试和运营一个能够完成真实任务的 AI
系统。

Carlo 的完整晚餐流程可以是：

1.  读取并核实个人偏好。
2.  将预算和配料禁忌转化为验收条件。
3.  通过受控工具连接查询菜单。
4.  使用适当的 Skill 执行筛选流程。
5.  根据工具返回的数据比较候选项。
6.  发现不合格结果时有限重试。
7.  独立验证配料和总价。
8.  向 Carlo 展示选择、依据和不确定性。
9.  获得授权后提交订单。
10. 检查真实订单状态并记录结果。

Jenkins 故障处理也可以采用类似结构：

``` text
Jenkins 失败事件
       ↓
收集日志、代码变更与构建上下文
       ↓
根据规格诊断根因并评估证据
       ↓
在受控环境中提出并实施最小修复
       ↓
运行测试、安全检查和回归验证
       ↓
根据反馈有限重试
       ↓
独立评估修复结果
       ↓
生成变更摘要、证据与剩余风险
       ↓
按授权策略提交或请求人工审批
       ↓
记录结果并持续监控
```

这里的关键不是把每个组件都做成一个独立
Agent，也不是让所有任务都完全自主运行。简单任务可以使用单次模型调用；复杂任务则可以组合工具、Skills、工作流、子
Agent 和评估机制。

真正重要的是：系统结构应与任务复杂度、失败成本和风险相匹配。

## 13. 这些技术如何放进时间线？

下表不是严格的"发明顺序"，而是用代表性时间点说明工程关注点如何变化。

  --------------------------------------------------------------------------------------------------------------------------------------------------
  时期                    代表性技术或实践                                                  解决的主要问题
  ----------------------- ----------------------------------------------------------------- --------------------------------------------------------
  2022--2023              结构化提示、Few-shot、Chain-of-Thought、ReAct、工具调用早期实践   让模型更好地遵循指令、分解任务，并尝试把推理与行动结合

  2023--2024              RAG、向量检索、长上下文、函数调用与 Agent 框架                    为模型提供外部知识，并让模型通过工具执行多步骤任务

  2024--2025              MCP、结构化输出、工作流编排、评测与护栏实践                       标准化工具连接，强化结果格式、执行边界和验证

  2025--2026              Agent Skills、个人 Agent、Harness Engineering、端到端 Agent       复用专业工作流程，让 Agent 在真实环境中更受控、更可维护
                          系统设计                                                          
  --------------------------------------------------------------------------------------------------------------------------------------------------

几个时间点值得特别留意：

-   **2022 年：** Chain-of-Thought 相关研究和 ReAct
    研究展示了多步推理以及推理与行动结合的潜力。
-   **2024 年 11 月：** Anthropic 公开推出 MCP，推动 AI
    应用连接外部数据与工具的标准化。
-   **2025 年 10 月：** Anthropic 推出 Agent
    Skills，采用可按需加载的目录形式封装专业任务知识。
-   **2025 年末至 2026 年：** 个人 Agent 和更完整的 Agent
    工程实践受到更多关注，执行边界、技能复用和可靠性逐渐成为系统设计的重点。

需要避免一种误解：这些技术并不是在某一年才第一次存在。例如，RAG、工作流、测试、权限控制和评估都有更早的历史。表格表达的是它们在现代
LLM 应用中的代表性发展与关注点，而不是宣称它们全部诞生于对应年份。

## 14. 工程师的角色：从亲手操作，到设计可靠的协作

传统的 Jenkins
故障处理需要工程师亲自读取日志、查找代码、分析根因、修改文件、运行测试和重新验证。

引入 Agent
后，其中一部分步骤可以自动化。但工程师的职责并不会简单消失，而是更强调系统设计与责任边界。

工程师需要决定：

1.  **哪些任务适合自动化？**
    重复、边界清晰、容易验证的任务通常更适合；高风险任务需要更严格的控制。
2.  **Agent 应该访问哪些上下文？**
    哪些来源可信、哪些数据可能过期、哪些信息不能暴露？
3.  **什么才算成功？** 需要用规格、测试和验收条件把目标说清楚。
4.  **Agent 可以执行哪些操作？**
    权限、隔离、审批、审计和停止机制应在设计阶段确定。
5.  **如何证明结果可靠？**
    不能只相信模型的自我报告，必须使用独立证据验证。
6.  **怎样持续改进系统？**
    通过失败记录、评测集、运行指标和人工反馈，发现系统性缺陷。

工程师正在从单纯的任务执行者，逐步转向 AI
工作流程的设计者、约束制定者和结果验证者。

## 15. 结语：从"回答得好"到"做得对，并能证明"

最初，我们问 AI：

> Carlo 是意大利人。你猜他喜欢什么 Pizza？

AI 可以给出一个合理的猜测。

随后，我们让它读取 Carlo
的真实偏好，明确预算与配料限制，查询真实菜单，比较候选项，并根据反馈调整选择。

最终，我们要求它不仅找到合适的
Pizza，还要在授权范围内完成任务，并用可靠证据证明结果符合要求。

Jenkins 的变化也一样：AI
从解释错误日志，逐步走向读取上下文、执行修复、运行测试、利用反馈调整，并在受控边界内交付可验证的结果。

Prompt Engineering、Context Engineering、Spec-Driven Development、Agent
Engineering、MCP、Harness Engineering、Loop Engineering、Evaluation
Engineering、Skills 和个人
Agent，并不是互相替代的单一路线。它们是构建可靠 AI
系统时可以组合使用的不同能力与工程实践。

**当 AI
从回答问题走向执行任务，工程的重点就从"如何让它说得更好"，转向"如何让它做得正确、受到控制，并且能够证明自己做对了"。**
