> Target release: **v0.11** (v0.10 = the prompt-evals harness, already built but
> not yet version-bumped — see `docs/v0.10-prompt-evals-plan.md`).
> Release steps for v0.11 follow `docs/CONTRIBUTING.md` § Release process:

## 1. Problem

The pipeline keeps asking questions that need **one bounded answer**, and
pays a full cloud chat call (or a dumb heuristic) for each one:

| Question asked today | Answered by | Cost of asking |
|---|---|---|
| Which visual component fits this scene? | regex classifier; falls through to `AnimatedIllustration` | wrong-but-cheap, or a full agent call to fix one scene |
| Does this QA finding block the render? | deterministic checks only | a human reads the report |
| Is this motion plan good enough to skip the cloud agent? | nothing — the cloud agent runs per scene | 1 cloud call per scene, every make |
| Is this draft good enough to publish? | full judge call | most expensive call in the pipeline |

**The shape** is a *System One* decision contract — `choice`, `score`,
`noul`, each with a confidence — and it is not ours by accident: the repo
already ran this experiment once and removed it. The **Laya** decision
layer (v0.6, deleted in `e681bda`) was a local re-implementation of a
System One model, and it measured *below chance* on the independent
benchmark (JevBench v1.2: Laya 421M — Intelligence **45.8**, Calibration
62.5). The lesson was not "decision layers are bad"; it was "**that** model
was bad".

So the layer stays, and this time it is **implemented here, over chat
models we already pay for** — no new service, no new vendor, no local
weights:

- `OpenAIDecisionProvider` — OpenAI's **Decisions API**
  (`POST /v1/decisions`): typed questions in, typed decisions with
  calibrated probabilities out.
- `MiniMaxDecisionProvider` — the MiniMax API, turned into a decision
  model by **function calling**: the option list is the schema's
  `enum`, and the answer is the tool call's arguments.

Because a decision model is only worth it if it is accurate enough,
cheap enough and fast enough for this pipeline, the layer ships with a
benchmark that says which provider wins — and the first measured run is
already in §7.6.

## 2. Goal

A provider-agnostic decision layer whose contract is a System One
contract — `choice` / `score` / `noul` with a confidence — implemented
over two chat APIs we already pay for, with a measurement that answers
**"which one is better: cost, speed, or accuracy?"** with numbers instead
of a preference.

No new vendor, no new service, no local model weights.

| Question | Answer |

## 4. The decision contract

The contract is a **System One** contract — `choice` / `score` / `noul`
with a confidence. We do not invent a shape and then ask two chat models
to imitate it; the shape is the one the repo's own removed Laya layer
already used, and the one TypeSafe's System One models publish.

Lives in `@video/llm` (`packages/llm/src/decision/`). It is **not** the chat
`Provider` interface: `ChatRequest`/`ChatResponse` cannot express a typed
answer with probabilities, and reusing them would let the existing provider
fallback machinery silently swap a decision for a different model (the exact
rejected integration in the old Laya plan, §3 there).

```ts
export type DecisionValue =
  /** `choice`: one named option, with the probability of every option. */
  | { kind: "choice"; choice: string; probabilities: Record<string, number> }
  /** `score`: probability-weighted average over the rubric levels.
   *  May fall between two integer levels (e.g. 1.7). */
  | { kind: "score"; score: number; legend: Record<string, string> }
  /** `noul`: the probability that a statement is true, 0..1.
   *  Not a boolean — 0.5 means "the model does not know". */
  | { kind: "noul"; probability: number };

export interface DecisionQuestion {
  id: string;
  /** What to decide. One wording, two transports. Loaded from the
   *  prompt registry, never inlined in source. */
  instructions: string;
  /** `choice`: option names → what they mean.
   *  `score`: ordered level descriptions.
   *  `noul`: optional `{ true, false }` criteria. */
  criteria?: Record<string, string> | string[] | { true: string; false: string };
  kind: DecisionValue["kind"];
}

export interface DecisionRequest {
  /** The state the decision is about (scene text, QA finding, article).
   *  A string, an object, or an array — a structured state beats a
   *  serialized blob. */
  state: string | Record<string, unknown> | unknown[];
  question: DecisionQuestion;
  /** Below this confidence the answer is treated as no answer. */
  minConfidence?: number;
}

export interface DecisionAnswer {
  value: DecisionValue;
  /** 0..1. For `noul`, the probability itself. For `choice`/`score`, the
   *  provider's confidence — and where it came from (see §6.2). */
  confidence: number;
  /** How the confidence was produced. Self-reported LLM confidence is not
   *  calibrated; a logprob-derived one is close. The bench measures the
   *  difference rather than assuming it. */
  confidenceSource: "native" | "logprobs" | "self_reported" | "vote";
  usage: { input: number; output: number };
  latencyMs: number;
  provider: string;
  model: string;
}

export interface DecisionProvider {
  readonly name: string;
  /** NEVER throws. Returns `null` when the provider is down, times out,
   *  answers outside the allowed options, or answers below
   *  `minConfidence`. The caller falls back to today's code path. */
  decide(req: DecisionRequest): Promise<DecisionAnswer | null>;
}
```

Three invariants (carried over from the removed Laya layer, which earned
them by being deleted for other reasons):

1. **Never throws.** A decision layer that can fail the pipeline is worse
   than no decision layer.
2. **Bounded.** An answer outside the question's criteria is `null`, not a
   best-effort guess.
3. **Degrade to current behavior.** `null` ⇒ the caller runs exactly the
   code path it runs today.

TypeSafe's System One guidance lands in the same place: *"A question that
asks the model to make the decision is usually at the wrong layer … write
the decision itself in code, where it's visible and testable."* Our §10
rule 4 is that guidance, made mechanical.

## 6. The two providers

The contract is a System One contract. The implementation is ours: a chat
model is asked ONE question and turned into a decision layer by the
technique below.

### 6.1 The technique — one typed question, two native mechanisms

Both providers answer the SAME question object; only the transport
differs, and each provider has a native mechanism for turning a chat
model into a decision model:

- **OpenAI — the Decisions API** (`POST /v1/decisions`). The question
  type IS the type system: `predicate`, `choice`, `score`. A `choice`
  question carries `choices: [{value, description?}]`; a `score`
  question carries `levels: [{label}]`. The answer comes back with a
  probability per option or level plus a calibrated `confidence`. The
  model never writes prose, so nothing has to be parsed or trusted.
- **MiniMax — function calling.** The question becomes a function whose
  parameters carry the answer: the option list is the `enum`, the model
  returns the chosen value, a `confidence`, and a one-sentence
  `reason`. The tool call is forced (`tool_choice`), so the answer
  cannot arrive as prose.

Both produce the same `DecisionAnswer`, so the benchmark compares
providers instead of comparing two different contracts.

### 6.2 `OpenAIDecisionProvider` — the Decisions API

| | |
|---|---|
| Endpoint | `POST ${OPENAI_BASE_URL ?? https://api.openai.com/v1}/decisions` |
| Auth | `OPENAI_API_KEY` |
| Model | `gpt-6-luna` by default (`OPENAI_DECISION_MODEL`) |
| Request | `{ model, input: <state>, questions: [{ name, type, instructions, choices?\|levels? }] }` |
| Answer | `predicate` → `{probability}` · `choice` → `{choice, probabilities[], confidence}` · `score` → `{score, probabilities[], confidence}` |
| Confidence | `confidenceSource: "native"` — the API's own calibrated probability |

Measured 2026-11-14 against the live API:

- question types are `predicate`, `choice`, `score`; `choices[0]` must be
  an OBJECT (`{value}`), `levels[0]` must be an OBJECT (`{label}`), and a
  question carries an optional `name` that the answer echoes back.
- **`gpt-4o-mini` and the `gpt-5` / `gpt-6.1` lines are not available on
  this endpoint** — they answer `model_not_found`. `gpt-6-luna` is the
  model that works.
- the answer's `confidence` is NOT the top probability (0.72 vs 0.86 on
  the same answer): the confidence is the model's own certainty, the
  `probabilities` array is the distribution.
- a `score` answer's `score` is the probability-weighted average of the
  levels (0.1 for a 90/10 split over levels 0 and 1) — the same
  "weighted average, may land between levels" semantics the contract
  defines.
- `output_tokens` is **0**: a decision costs input tokens only.

### 6.3 `MiniMaxDecisionProvider` — function calling

| | |
|---|---|
| Endpoint | `POST ${MINIMAX_API_HOST ?? https://api.minimax.io}/v1/chat/completions` |
| Auth | `MINIMAX_API_KEY` |
| Model | `MiniMax-M3.1-Flash` by default (`MINIMAX_DECISION_MODEL`) |
| Request | `tools: [{ type: "function", function: { name, description, parameters } }]` + a forced `tool_choice` |
| Schema | `{ <result>: { type: "string", enum: <options> }, confidence: { type: "number" }, reason: { type: "string" } }` — required |
| Answer | the tool call's JSON arguments |
| Confidence | `confidenceSource: "self_reported"` (one call) or `"vote"` (`samples: k`) |

The schema is the type system: the option list IS the `enum`, so the
model cannot answer outside it, and the local check proves it did not.

Measured 2026-11-14, three facts that shaped the class:

1. **The tool call works**, and comes back as
   `choices[0].message.tool_calls[0].function.arguments` (a JSON string).
2. **The model reasons first, and it reasons a lot**: a one-line
   question cost 491 prompt tokens, 427 reasoning tokens and 598
   completion tokens. The chat API gives no `logprobs`, so the
   distribution has to come from sampling (`samples: k` → the vote
   distribution) — which is where the extra tokens go.
3. **The output budget must cover the reasoning**: at `max_tokens: 512`
   the call ended with `finish_reason: length` and NO tool call at all.
   The default here is 2048 for that reason.

### 6.4 How each provider bounds the answer

| | OpenAI | MiniMax |
|---|---|---|
| Bound by | the request's `choices` / `levels` | the schema's `enum` |
| Wrong-type answer | impossible (the API types the answer) | impossible (the enum) |
| Answer outside the bound | rejected locally → `null` | rejected locally → `null` |
| Free-text by-product | none | `reason` — one sentence, kept for the decision log |

## 7. The benchmark — cost / speed / accuracy

The bench measures the **same four axes JevBench uses** — Intelligence,
Calibration, Speed, Cost — but on *this pipeline's* corpus, because
JevBench's corpus is not our corpus.

### 7.1 Corpus

`packages/prompts/evals/decisions/<case-id>.yaml`, same fixture shape as the
existing golden sets:

```yaml
id: qa-blocking-finding
surface: qa-triage           # which question body to load
input:
  state: |
    Rendered frame 12 of 23. Text overlaps the lower-third caption
    band from 00:41 to 00:44.
expects:
  value: { kind: "choice", choice: "block" }
provenance:
  source: "Real QA report 2026-10-31, finding F-07 (caption collision)."
```

Rules for the corpus (enforced by a test, like the prompt-evals orphan guard):

- Every case names a `surface` whose question body exists in the registry.
- Every case carries an `expects` — **no unlabeled cases**. A corpus without
  labels cannot measure accuracy.
- The corpus spans **both languages** (zh-CN and en-US): the removed Laya
  layer had a CJK routing path, and a zh-only corpus would hide that.
- Cases come from real failures (`provenance.source` required), not invented
  ones — the same rule the prompt-evals corpus follows.
- `noul` cases carry a probability band (`expects.probability: [0.8, 1.0]`),
  not a boolean, so calibration can be scored.

### 7.2 Runner

`video decision bench` (mirrors `video prompts eval`):

```
video decision bench [--provider openai|minimax|all] [--surface qa-triage]
                      [--case <id>] [--repeat 3] [--model <id>] [--json]
```

- `--repeat N` — each case runs N times, so latency percentiles mean
  something and one flaky answer does not decide the winner.
- One JSON report per run: `runs/decision-bench-<ts>.json` + a markdown
  table on stdout.
- Tests use mocked `fetch` — no provider is contacted in CI.
- A provider with no key is reported as **unavailable** (with the missing
  env var named), not skipped silently.

### 7.3 Metrics

| Axis | Definition |
|---|---|
| **accuracy** (Intelligence) | `choice` → exact match (trimmed, case-insensitive). `score` → `|answer − expected| ≤ tolerance` (per case, default 0.05). `noul` → the expected side (probability ≥ 0.5 or < 0.5) matches. An unparseable or out-of-bounds answer counts as **wrong**, never as "skipped". |
| **calibration** | Brier score over `noul` cases: `mean((p − y)²)`. 0 = perfect, **0.25 = "always answer 0.5"**. Reported per provider, because a self-reported confidence scores near 0.25 and hides behind a good accuracy number. |
| **latency** (Speed) | p50 and p95 over all calls of a provider, in ms, measured client-side around the HTTP call. |
| **cost** (Cost) | `tokens_in × price_in + tokens_out × price_out`, prices read from `llm.config.yaml`. **A missing price is `n/a`, never `0`** — the repo already shipped one fabricated `usage 0/0` bug; the bench must not repeat it. |
| **parse failures** | answers that needed local repair or were rejected. A provider with a high parse-failure rate is not "accurate" at a discount. |

### 7.4 Which one is better — the ranking rule (deterministic code)

No LLM picks the winner. The rule lives in the bench code:

1. **Eligibility.** A provider is eligible only if
   - accuracy ≥ `--min-accuracy` (default 0.90) **and** ≥ the deterministic
     baseline's accuracy on the same corpus, **and**
   - Brier score ≤ `--max-brier` (default 0.25 — better than "always 0.5").
2. **Rank eligible providers** by cost per decision (ascending), then by p95
   latency (ascending).
3. **Report all four axes** in the table regardless of ranking, so a provider
   that wins on price but loses on calibration is visible, not hidden.

The rationale: a decision that is wrong is not a cheaper decision, it is a
bug. Price only separates providers that are both right often enough. And
calibration gates because this layer *uses* confidence to decide when to
degrade — an uncalibrated confidence is a worse silent failure than a
missing one.

### 7.5 Measured on the corpus — final post-fix run (2026-11-15)

The corpus is **187 labeled cases across 4 surfaces**
(`packages/prompts/decisions/<surface>/<case-id>.yaml`), every one of them
sourced from a real artifact in this repo — a shipped render report, a
shipped article review (the large majority come from the attempts the
review loop actually ran), a shipped storyboard scene, or a unit-test
fixture that encodes a real classification. (The 10 visual-class cases
were retired with structured routing in v0.12; 176 of the cases are
draft-bar, derived from shipped review artifacts with NO human
labelling — the label is `verdictToLabel()` of the artifact's own
verdict, re-checked by the loader.)

Same-corpus apples-to-apples run (2026-11-15, after the §7.7 wording fix
and the §7.8 rule fix — both providers, current wordings):

| provider | model | accuracy | brier | p50 | p95 | cost/decision | eligible |
|---|---|---|---|---|---|---|---|
| **OpenAI Decisions API** | gpt-6-luna | **174/187 (0.930)** | **0.000** | **149 ms** | **308 ms** | n/a | **✅ eligible** |
| MiniMax function calling | MiniMax-M3.1-Flash | 149/187 (0.797) | 0.007 | 2,449 ms | 7,783 ms | n/a | ❌ accuracy < 0.9 |
| deterministic path (today) | — | 0.500 | — | — | — | free | — |

Per surface — the corpus is lopsided by construction (the draft loop
writes a review artifact per attempt; the render QA surface produces one
warning type), so the per-surface numbers are the ones that compare like
with like:

| surface | cases | OpenAI | MiniMax |
|---|---|---|---|
| qa-triage | 7 | **7/7** (1.000) | **7/7** (1.000) |
| caption-overlap | 2 | **2/2** (1.000), brier 0.000 | **2/2** (1.000), brier 0.007 |
| motion-prescreen | 2 | **2/2** (1.000) | **2/2** (1.000) |
| draft-bar | 176 | **163/176 (0.926)** | 138/176 (0.784) |

What the final run says:

1. **The wording fix helped BOTH providers, dramatically.** MiniMax went
   from 0.447–0.625 (pre-fix chaos) to **0.797** — perfect on three of
   four surfaces, best-ever brier (0.007). The severity-anchored wording
   was the bottleneck for both models.
2. **OpenAI wins every axis and the gate clears only for it** (0.930 ≥
   0.9): +13 points of accuracy, 16× faster at p50 (149 ms vs 2,449 ms),
   25× at p95 (308 ms vs 7,783 ms), brier 0.000 — perfectly calibrated
   on every run, while MiniMax's brier ranged 0.006 → 0.941 across the
   pre-fix runs. The default stands on measurement.
3. **MiniMax is now a plausible fallback** for draft-bar (0.784, brier
   0.007 on this run) — though one good run does not overturn the
   documented instability; re-measure after the next quota cycle before
   relying on it.
4. **The remaining gap is entirely draft-bar** (0.926 vs 0.784): the
   surface whose answer is a threshold rather than a fact.

**The screen stays cancelled.** Even at 0.797, a pre-judge screen saves
only the drafts the model passes confidently — measured at 2.3% (§7.7) —
and as a stop signal it would kill the loop's recovery.

The cost column reads `n/a` for both providers: no per-token price was
verified for `gpt-6-luna` or `MiniMax-M3.1-Flash`. The token counts are
known, so the ranking is one config lookup away.

## 7.7 The verdict, per surface — and the wording fix

The corpus now measures five surfaces, and the per-surface numbers say
where a decision model earns its keep in THIS pipeline:

| surface | cases | the model | today's path |
|---|---|---|---|
| qa-triage | 7 | **7/7** | n/a (a human reads the report) |
| caption-overlap | 2 | **2/2** (brier 0.000) | n/a (the render validation catches it) |
| motion-prescreen | 2 | **2/2** | the per-scene motion call |
| visual-class | 10 | **8/10** | the keyword classifier: **6/10** |
| **draft-bar** | **176** | **143/176 (0.813)** | the review's own verdict |

**The draft surface's story is the calibration experiment.** The first
measurement found the model answering one notch stricter than the review's
verdict — 108 of 174 real consults said `reject` where the review said
`revise` — and the per-grade cross-tab showed the offset was uniform, not
random. That pointed at the WORDING, not the model's capability.

`scripts/experiment-decision-question.mjs` tested four wordings of the
same question over the same 176 cases, with a train/test split for any
post-hoc shift:

| wording | raw accuracy | screen: judge calls saved | false passes |
|---|---|---|---|
| v1 production (the old wording) | 29.5% | 3.4% | 0 |
| v2 editorial volume | 76.7% | 2.3% | 0 |
| **v3 severity-anchored** | **82.4%** | 16.5% | 18 |
| v4 editorial outcome | 79.0% | 5.7% | 3 |

**v3 won, and its wording is now production.** The fix is one sentence
that names what a Major finding means: *"A Major finding means 'this part
must be fixed'. On its own it does not mean 'rewrite the draft'."* The
boundary the model was missing was the definition of the boundary. Raw
verdict accuracy on draft-bar went **0.415 → 0.813** on the full corpus,
and the corpus overall went **0.467 → 0.822**.

**The screen is still not built — but for a new reason.** v3's raw
"pass" answers would skip 16.5% of judge calls, but 18 of those 29 are
drafts the review loop actually REVISED (`passing: false` — the loop kept
polishing and burned more judge calls on them). With a confidence gate
(≥ 0.6) the screen saves 7.4% of judge calls at 77% precision; the
editorial-outcome wording (v4) at the same gate saves 4.0% at 100%
precision. Four to seven percent of one call per attempt is not a feature
— the draft generation, not the judge, dominates the loop's cost. And the
safety property held everywhere: **no wording ever said `pass` where the
review said `reject`** (0 in 176, every variant, every gate).

So the final shape of the feature: the decision layer is a **measurement
and audit layer**, live in `shadow`, growing the corpus from production.
It is not a gate and not a screen. The bench reports its accuracy per
surface; the numbers are honest; the gate (0.9) stays unclosed because
0.822 is below it — and the remaining draft-bar misses are the
`pass`/`revise` boundary, which is the review's own judgement call.

**And the rule did not change.** The corpus's labels stay the artifact's
own verdict. The offset turned out to be the wording's — fixing the
question moved the model, and the labels never moved.

## 7.8 The rule fix — the label now matches what the loop does

After the wording fix the draft-bar surface sat at 0.813, with the
remaining misses concentrated on six artifacts that contradict
themselves: `passing: true` **and** `MAJOR_REVISION_NEEDED`. Reading the
loop's actual gate settled them: `passesBar` (packages/draft/src/
article-review.ts) blocks **only on a Critical finding** — the
`MAJOR_REVISION_NEEDED` flag is advisory, and the loop SHIPS drafts that
carry it. Six shipped artifacts hold `passing: true` plus the flag.

The first version of the `review-verdict` rule misread that flag as a
revise. The fix aligns the rule with `passesBar`:

- `reject` — a Critical finding (`CRITICAL_BLOCKER`).
- `revise` — `passing: false`.
- `pass` — `passing: true`, whatever the flags say.

Six labels moved (`revise` → `pass`), the loader's re-derivation kept
every fixture honest, and the production wording gained the matching
sentence: *"a draft the review passed ships, whatever the risk flags
say."* The state already carried `passing true`; the wording now tells
the model what the pipeline does with it.

**Result: draft-bar 0.813 → 0.926, corpus 0.822 → 0.924 — the gate
clears.** And neither fix touched a label by hand: the wording fix moved
the model, the rule fix moved six labels that contradicted the artifact
they cite, and the loader verified every one of the 176.

| step | draft-bar | corpus |
|---|---|---|
| first measurement (old wording, misread rule) | 0.415 | 0.467 |
| + severity-anchored wording | 0.813 | 0.822 |
| + rule aligned with `passesBar` | **0.926** | **0.924** |

## 8. Where decisions plug in

All four are **advisory**. None replaces a human gate or a workflow state
transition (the pipeline's 10-state machine is deterministic and
replay-verified — ML confidence inside a transition breaks that contract).

| Surface | Today | With a decision |
|---|---|---|
| D1 motion pre-screen | cloud agent runs per scene | skip the cloud call when the baseline plan passes the decision |
| D2 visual classifier fall-through | regex miss → `AnimatedIllustration` | decision picks the component from the registry list |
| D3 QA triage | deterministic checks only | **WIRED** — each finding carries an advisory `pass/review/block` (+ confidence) in the report; never gates (`--strict` reads `level`) |
| D4 draft quality bar | full judge call | decision screens obviously-bad drafts before the expensive judge |

Order of implementation: **D2 → D3 → D1 → D4**. D2 and D3 are cheap to
measure and cannot break a render; D1 touches the costliest path; D4 sits in
front of the most expensive call and needs the most corpus work.

**Non-goals:** replacing the article judge, replacing the review agent,
anything inside the workflow state machine, anything a human gates.

## 9. What this reuses from the removed Laya layer

The Laya decision layer shipped in v0.6 and was removed in `e681bda`
(`remove laya`). Its design is prior art and its failure is the warning:

- **Reused:** the `choice` / `score` / `noul` vocabulary, the never-throws
  contract, the shadow-first rollout, the "degrade to current behavior"
  fallback, the decision sidecar as the audit trail.
- **Not reused:** the local encoder service. It scored the triage question
  at `confidence 0.0075` (near-uniform) and, on the independent benchmark,
  below chance on intelligence. The calibration gate had to be mandatory,
  and the corpus still had to be zh+en. A calibrated cloud model is cheaper
  to reason about than a miscalibrated local one.
- **Lesson carried:** every decision is recorded with its baseline, so
  "did the decision agree with what actually ran?" is answerable after the
  fact instead of argued about.

## 10. Safety rules

1. **Advisory only.** A decision never replaces a human gate and never
   drives a workflow state transition.
2. **Degrade.** `decide()` never throws; `null` ⇒ today's code path. A
   failed call is an error, never an answer — TypeSafe's rule, and the
   reason the provider returns `null` instead of a default.
3. **Shadow first, then on.** `DECISION_MODE=off|shadow|on`. The layer
   shipped defaulting to `off`; the gate cleared on 2026-11-14 (0.924 ≥
   0.9, brier 0.000 — §7.5) and the default flipped to **`on`**, the same
   promotion pattern flux used in v0.5.3. `on` and `shadow` behave
   identically today — both record, nothing acts, because no acting
   surface is wired; the two names diverge the day one ships. `off`
   exists for turning the layer off without a code change, and the
   vitest global setup pins it so the test suite stays hermetic. A run
   without a provider key skips cleanly with one stderr line.
4. **Deterministic code owns branching.** When to consult a decision, how to
   fall back, and how to score agreement are `if` statements, never model
   output. (TypeSafe: *"write the decision itself in code, where it's
   visible and testable."*)
5. **Recorded.** Every consult writes one row to
   `<project>/decision-log.jsonl`: `{ts, surface, provider, model, mode,
   state_sha256, answer, confidence, confidence_source, baseline, agreed,
   latency_ms, usage}`. The raw state is hashed, not stored.

## 13.1 The corpus after the backfill

174 real consults across the 55 shipped projects' review artifacts landed
in the corpus (165 new draft-bar cases; the corpus is now 197). Every one
of them is labelled by the `review-verdict` rule from the artifact's own
verdict — no human labelled any of them.

The measurement they produce is the sharpest result in this document:

| | |
|---|---|
| The decision model's agreement with the review's verdict | **28%** (49/174) |
| The model's answer vs the review's | `reject` vs `revise` **108** · `revise` vs `revise` 43 · `revise` vs `pass` 16 · `pass` vs `pass` 4 · `reject` vs `reject` 2 · `reject` vs `pass` 1 |
| The one thing it never does | say `pass` where the review says `reject` |

That is a threshold shift, not noise: the model reads "this needs real
work" as `reject` where the review reads it as `revise`. It finds the
problems; it does not reproduce the review's line. Which line is right is
a human's call — and that is the surface where a decision model cannot
replace the thing that draws the line.

**§16.1 The A/B and the constraint strategy (2026-11-15).** Same prompt,
both models, 1280×720, using the real shipped scene brief (1457 chars)
and thumbnail prompt (304 chars):

| variant | latency | input tokens | est. cost |
|---|---|---|---|
| image-01 (scene) | 15.5 s | n/a | n/a |
| **H3 enhancement ON** | 11.0 s | 3967 (the rewrite) | $0.0246 |
| **H3 enhancement OFF** | **8.0 s** | 335 (verbatim brief) | **$0.0163** |

The quality call is the operator's (the comparison sheets live at
`/tmp/h3-vs-01/*-row.jpg`); the MEASURED facts: H3 is faster in every
variant, enhancement roughly doubles the input cost (it re-authors the
brief into English prose — the 304-char Chinese thumbnail prompt came
back as 4973 tokens of Ghibli-styled prose), and the rewrite preserved
the opening constraints (left-third composition) in both 400-char
samples.

**The adopted strategy — enhancement ON, constraints GUARANTEED by code:**
`constraintGuard` in the provider. The caller's hard constraints are
auto-extracted from the prompt (every `#RRGGBB` hex, plus "no text");
after an enhanced generation the provider checks the returned
`revised_prompt` for them, and if the rewrite dropped one it re-generates
ONCE with the verbatim brief (enhancement off). Deterministic code, one
extra call worst-case, and it composes with the user's preference:
they chose the enhanced look, the guard keeps the contract the pipeline
depends on (palette lock, no-text band, overlay zone).

## 15. Provider decision (2026-11-14)

**OpenAI Decisions API is the default provider, and the layer is ON by
default** — both are in code (`createDecisionProvider` defaults to
`openai`; `resolveDecisionMode` defaults to `on`; `DECISION_PROVIDER` /
`DECISION_MODEL` / `DECISION_MODE` override per run), and this section
records why and what would change either.

**Why, per axis (measured, §7.5):**

| axis | OpenAI | MiniMax |
|---|---|---|
| accuracy | **0.924** (eligible) | 0.447 (ineligible) |
| calibration | brier **0.000** on every run | 0.006 → **0.941** across seven runs |
| speed | **219 ms** p50 / **442 ms** p95 | 4,963 ms / 24,274 ms |
| cost | n/a | n/a |

OpenAI wins four surfaces of five outright and the fifth too (8/10 vs
6/10). The bench's ranking rule (accuracy gates, then cost, then latency)
never reached cost because MiniMax never cleared the accuracy gate.

**Two caveats kept next to the decision:**

1. **The cost column is still `n/a`.** The default is decided on
   accuracy + calibration + speed alone. If a verified price table ever
   makes MiniMax an order of magnitude cheaper, the honest comparison is
   one bench run away — but MiniMax would still have to clear the
   accuracy gate first.
2. **MiniMax's draft-bar row is a pre-fix measurement, and the re-run hit
   the plan's monthly quota.** The wording and rule fixes (§7.7–7.8)
   came after its last full run. A re-run was attempted on 2026-11-14
   and every call returned `429 Token Plan usage limit reached (2056)` —
   the key runs on MiniMax's paid monthly plan, which is available MOST
   of the time but exhausts under load, and the measurement campaign
   (the 197-case run, the 176×4 wording experiment, the 174 backfill
   consults) spent the month's budget in one day. Two consequences,
   neither of which changes the default:
   - the caveat stays open — MiniMax's accuracy under the current
     wording is unknown until the plan resets;
   - when the quota IS out, the layer degrades exactly as designed:
     `decide()` returns null, the shadow rows carry the error, and the
     pipeline runs the deterministic path. Availability is the third
     reason OpenAI is the default — the other two (accuracy,
     calibration) are measured above.

**What would revisit the decision:** a provider that clears the gates at
a lower verified cost; or an OpenAI outage pattern. MiniMax stays the
natural FALLBACK — it is paid monthly and available most days — but no
fallback chain is built: in shadow mode a mid-run provider switch would
mix two models in one log (each row records its provider, so it is
visible, but comparability suffers), and outside shadow there is nothing
to fall back TO yet — the layer's job is to measure, and it degrades to
the deterministic path when its provider is unavailable, whatever the
reason.
