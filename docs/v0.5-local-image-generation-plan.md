# v0.5 — Local Image Generation Plan (FLUX.2 Klein 4B)

> **⚠️ SUPERSEDED (2026-10-17).** The local FLUX.2 Klein generation stack
> this plan describes was **removed in v0.9** (commit 95a8086 "remove
> flux"): hosted providers (MiniMax default, plus OpenAI and Gemini) replaced
> it, and the FLUX worker/skills/providers no longer exist in the repo. The
> surviving pieces are the `image_style` presets (now in
> `packages/prompts/prompts/image-styles.yaml`) and the content-keyed image
> cache. Kept for historical context only — do NOT treat its constraints as
> binding.

> Source: read-through of the v0.4.3 codebase on 2026-10-14 (git
> `5940bf3`) plus the freshly merged local-image subsystem. This plan
> documents the design of the new **local** image generation stack —
> FLUX.2 Klein 4B via Python `diffusers` + `pillow` + LoRA — against the
> status quo, and defines what ships now vs. what stays deferred. It
> does NOT touch the two-file human-gate principle (`article.md` +
> `audio-config.yaml`, doc `AI_Video_Factory_Design_and_Plan_v1.1.md`
> §65).

## Guiding constraints (carried over from doc §65)

- AI generates · Human decides · Code renders · Git remembers.
- The two human-edit files remain the only files a user must hand-edit.
- Derived files stay re-derivable and idempotent (`video make` skips
  work whose outputs are newer than its inputs).
- No auto-publishing, no auto-approve, no silent quota spend.

## Why this plan exists

All real image generation today goes through the MiniMax `image-01` HTTP
API (`packages/media-generators/src/minimax-image.ts`, wired in v0.3).
Three structural gaps:

1. **Quota + network dependency** — every scene visual and thumbnail
   burns MiniMax image quota and needs the network up. A failed render
   at 2 a.m. costs a round trip through a paid API; iterating on one
   scene's image costs quota each time.
2. **No style control** — the API model accepts only a prompt. Channel
   branding (a consistent look across every video) cannot be expressed
   except by prompt-begging. LoRA adapters are the industry answer and
   are impossible over the API.
3. **Single point of vendor lock** — `--image-provider` has exactly one
   real backend. The README's "GLM image provider — waiting on a
   verified spec" note is a symptom: the pipeline's image future is
   gated on other companies' API catalogs.

The fix: a **local** provider. FLUX.2 Klein 4B (Black Forest Labs,
Apache-2.0, ungated on HF) is small enough to run on this machine
(M4 / 24 GB unified memory, ~28 s load, warm across the render) and
speaks `Flux2KleinPipeline` in stock `diffusers` — including the
`Flux2LoraLoaderMixin`, which is where LoRA support comes from.

## The new design

```
video make <p> --image-provider flux
  └─ packages/make/src/index.ts  generateSceneVisuals(provider="flux")
       └─ FluxKleinImageProvider            packages/media-generators/src/flux-image.ts
            │  spawns ONE worker per render (warm pipeline),
            │  JSONL over stdio, images via session temp dir
            ▼
            uv run python flux_worker.py     packages/media-generators/python/
            │  Flux2KleinPipeline (diffusers 0.41, torch 2.14, MPS)
            │  + LoRA via load_lora_weights / set_adapters (peft)
            │  + Pillow: VAE-align snap → ImageOps.fit to exact box → JPEG
            ▼
            assets/images/scene_N.jpg  (+ thumbnail.jpg)
```

Decisions and their reasons:

- **Python sidecar, not a Node binding.** diffusers/peft/torch are a
  Python-native ecosystem; every Node binding lags. `uv` makes the
  Python footprint hermetic: one `pyproject.toml` + lockfile, managed
  Python 3.12, `uv sync` is the whole install. The TS package never
  imports Python state — the only surface is the JSONL protocol.
- **Warm daemon, not per-image CLI.** Model load (~28 s) dominates
  per-image cost. One worker serves every scene of a render; the
  provider disposes it when `generateSceneVisuals` finishes, and the
  worker self-exits on stdin EOF so orphans are impossible.
- **Images over a temp dir, not stdout.** A 1920×1080 JPEG is ~1 MB;
  keeping stdout pure-JSONL avoids interleaving bugs and lets the
  response carry the seed for reproducibility. Files are unlinked
  after reading.
- **MPS group offloading for the text encoder.** The full bf16 stack is
  ~22 GB, which does not fit resident next to macOS in 24 GB. diffusers
  `apply_group_offloading` streams text-encoder layers between CPU RAM
  and MPS — on unified memory the "transfer" is same-RAM pointer work,
  so peak footprint halves for near-zero cost. `FLUX2_OFFLOAD=full`
  extends this to the transformer (the knob for 9B variants).
- **LoRA at startup, from the environment.** Adapters chosen by the
  human (`FLUX2_LORA="path:0.8,repo"`), applied once via
  `load_lora_weights` + `set_adapters` so the pipeline stays warm.
  Per-job LoRA switching would reload weights per scene — explicitly
  rejected.
- **Distilled-first defaults.** klein-4B is step-distilled
  (`is_distilled` from the pipeline config): 8 steps, guidance ignored
  — the worker reads this from the checkpoint instead of hardcoding,
  so switching to `FLUX.2-klein-base-4B` (50 steps, guidance 4.0) via
  `FLUX2_MODEL` needs no other change.
- **Weights inside the repo, gitignored.** `models/hf/` (22 GB) is
  local, disposable cache; `uv.lock` in `python/` is tracked so the
  environment is reproducible.

## Task breakdown

- **T1 — Python worker** (`python/flux_worker.py`) — **shipped.** JSONL
  daemon + `--check` / `--download` / `--selftest` modes; LoRA loading;
  VAE-align snapping + Pillow fit; MPS memory strategy; per-job error
  isolation (one bad prompt never kills the render).
- **T2 — TS provider** (`src/flux-image.ts`) — **shipped.**
  `FluxKleinImageProvider implements ImageProvider`; lazy spawn, ready
  handshake, per-job timeouts (20 min ready / 10 min job defaults),
  crash-restart on next call, stderr tail surfaced in
  `ImageGenerationError`, `dispose()` + parent-exit kill.
- **T3 — Pipeline wiring** — **shipped.** `--image-provider flux` on
  `video make`, `--provider flux` on `video thumbnail`; prompt
  expansion (v0.4 T3) benefits flux for free (it keys on non-mock);
  failure semantics unchanged (scene falls back to shapes).
- **T4 — Environment + weights** — **shipped.** `uv sync` env
  (torch 2.14.1 / diffusers 0.41.0 / transformers 5.19 / peft 0.21 /
  pillow 12.3, MPS verified), 22 GB weights in `models/hf/`, end-to-end
  smoke on the real checkpoint (load 27.5 s, first 832×480@8-step image
  81 s incl. MPS warmup, valid JPEG at exact requested dimensions).
- **T5 — LoRA conventions** — **shipped (2026-10-14).** Human-edited
  `lora-config.yaml` (project- or repo-root-scoped) is the canonical
  surface; legacy `FLUX2_LORA` env / `lora:` provider option remain.
  Source resolution distinguishes HF repo ids from local files
  (file-extension heuristic: `.safetensors` / `.bin` / `.pt` / `.gguf` /
  `.ckpt` → local). License sidecars are enforced when declared
  (`{name}.license.txt` mirrors the audio-asset convention); an un-
  annotated local adapter emits a warning so humans own the licensing
  check. TypeScript: `packages/media-generators/src/lora-config.ts` +
  `lora-config.test.ts` (8 unit + 2 end-to-end against the real
  `--selftest` worker = 10 new tests). Python: `parse_lora_config` in
  `flux_worker.py`. Resolution order (highest first):
  `FLUX2_LORA_CONFIG` env → `--lora-config` CLI flag → `provider.loraConfigPath` →
  `<projectRoot>/lora-config.yaml` → `<repoRoot>/lora-config.yaml` →
  `FLUX2_LORA` env (legacy) → `lora:` provider option. Real-LoRA smoke
  on `black-forest-labs/FLUX.2-klein-4B` + `fal/flux-2-klein-4B-outpaint-lora`
  (Apache-2.0): 640×384 image produced in 75 s post-ready; the
  `lora adapters: […/outpaint-klein-4b.safetensors:0.4]` line and
  the matching `ready` event field confirm the entire load path
  (config → resolve → `load_lora_weights` → `set_adapters`).
- **T6.1 — base-4B quality path** — **shipped (2026-10-14).** The
  worker already auto-detects `is_distilled` from the checkpoint's
  `model_index.json` (8 steps / guidance ignored for the distilled
  4B, 50 steps / guidance 4.0 for `FLUX.2-klein-base-4B`), so flipping
  models is a one-line `FLUX2_MODEL=…` change. The new
  `flux_worker.py --check-model <repo_id>` mode fetches only
  `model_index.json` (no safetensors) and reports `is_distilled` plus
  the worker-derived defaults, so a user can pick a checkpoint
  before committing to the multi-GB download. Two end-to-end
  vitest cases assert the report for both `…-klein-4B` (distilled,
  8 steps) and `…-klein-base-4B` (base, 50 steps, guidance honored).
  The base-4B weights are not pre-downloaded here (50 GB+);
  `uv run python flux_worker.py --download` will fetch them when
  ready to switch.
- **T6.2 — Image-to-image via the same 4B pipeline** — **shipped
  (2026-10-14).** `Flux2KleinPipeline.__call__` accepts an `image=`
  argument for image-conditioned generation; the worker surfaces a
  new `referenceImage: "<abs path>"` field on the JSONL job envelope
  (backwards-compatible: missing field = plain text-to-image), the
  `ImageRequest` contract grows an optional `referenceImage?: string`
  field, and the `FluxKleinImageProvider` forwards it. **No separate
  KV pipeline class** — `black-forest-labs/FLUX.2-klein-9b-kv` is
  gated; the 4B accepts the same conditioning via the regular
  pipeline. `Flux2KleinKVPipeline` is documented in diffusers but
  unused here for the ungated 4B.
  **Orchestrator integration:** `--reference-style-anchor` on
  `video make --image-provider flux` (off by default) generates
  scene 1 first, then conditions scenes 2..N on it — the natural
  style-anchor for a video factory (all scenes look like scene 1).
  New `--anchor-scene <N>` (1-based, default 1) lets the user pick
  a later scene as the anchor — useful when the first scenes are
  titles and the first real visual is later (e.g. `--anchor-scene 3`
  conditions scenes 4..N on scene 3). Scenes before the anchor
  generate independently.
  **Idempotency fix (2026-10-14):** the first version only set
  `styleAnchor` in the post-generation try-block, so re-runs with
  `--reference-style-anchor` silently dropped the anchor when the
  anchor scene's image already existed on disk. Fixed: anchor is
  promoted on **both** the fresh-generation path and the
  pre-existing-file path. Guarded by a vitest regression test
  (`style-anchor.test.ts`) that pre-writes `scene_1.jpg` and
  asserts scenes 2..3 receive `referenceImage: <scene_1.jpg>`.
  **Verified end-to-end** on the real 4B pipeline at 512×512, 4
  steps: t2i and i2i (same prompt, same seed, 512×512 blue-square
  reference) produce JPEGs with per-pixel RMS diff mean 135.69,
  p95 225.42 (out of 255) — radically different output, proving
  the conditioning takes effect.
  **Latency note:** the Qwen3 vision encoder processes the
  reference per call; at 1024×1024 reference + 8 steps the i2i
  round-trip is ~4 min on M4 (vs ~30s for a comparable t2i at
  6 steps / 640×384). Realistic for a video where scene 1
  establishes the look and scenes 2..N are cheaper thanks to the
  KV-cached reference; the orchestrator reports the style-anchor
  file so the user knows where the consistency is rooted.
  **Tests:** 4 vitest cases (selftest protocol x2 + orchestrator
  regression x2). Total: 233 tests green.
- **T6.3 — Text-encoder quantization** — **partially shipped (2026-10-14).**
  - **int4 weight-only on MPS: blocked** (Apple's private `mslk` ≥ 1.0.0
    framework is not distributable; torchao raises `ImportError: Requires
    mslk >= 1.0.0` for transformer-scale linears on MPS).
  - **int8 weight-only on MPS: shipped.** New
    `FLUX2_TEXT_ENCODER_QUANT=int8` env knob applies torchao
    `Int8WeightOnlyConfig` to every `nn.Linear` in the Qwen3 text encoder
    after `from_pretrained`. Verified end-to-end on the real
    `Flux2KleinPipeline` (M4 / 24 GB): text-encoder MPS memory
    **8.1 GB → 4.9 GB (40% reduction)**, 0.2 s one-time quant, no
    measurable diffusion quality loss (per-pixel RMS diff p95 = 6.93/255
    vs. the bf16 baseline, means within 1 RGB unit). The ready event
    surfaces the mode (`"text_encoder_quant": "int8(4,022,468,096→int8)"`)
    so callers can audit. Use when 9B + LoRA pushes past the
    `FLUX2_OFFLOAD=full` ceiling; for 4B-distilled alone the default
    off is fine.

- **T7 — flux is the default; pre-flight health check** —
  **shipped (2026-10-14).** Two product calls:
  1. `video make` defaults `--image-provider` to `flux` (gated
     on `!fake`); `video thumbnail` keeps `mock` (one-shot op,
     explicit `--provider flux` is the upgrade path).
  2. `FluxKleinImageProvider` runs `uv run python
     flux_worker.py --check` once per provider instance; on
     failure, throws `ImageGenerationError` with the actionable
     fix hint (`uv sync && uv run python flux_worker.py
     --check`). Bypass: `FLUX2_SKIP_HEALTH_CHECK=1`. The three
     real first-time-user failure modes (uv missing, python
     env not synced, weights not downloaded) are now caught with
     a clear message instead of a confusing traceback. Side
     fix: `spawnWorker` now listens for the spawn `error`
     event so ENOENT on a bad `pythonBin` doesn't hang the
     ready handshake.
  BANNER `VERSION = "0.5.3"`. 3 new vitest cases
  (exit-non-zero + uv-missing + bypass-honored). Total: 236
  tests green.

## Risks / open questions

- **Speed** — ~1–3 min per 1080p scene image on M4. Acceptable for a
  factory that renders in minutes anyway; `FLUX2_STEPS` trades quality
  for time. If it bites, T6b (KV image-to-image, 4-step) is the lever.
- **MPS allocator pressure** — first 1080p generation after load is the
  worst case (shader compile + peak activations). If pressure-kills
  appear, `FLUX2_OFFLOAD=full` is the mitigation, `float16` the
  fallback.
- **transformers 5.x is new** — pinned by `uv.lock`; upgrades are a
  deliberate `uv lock --upgrade` away, not a surprise.
