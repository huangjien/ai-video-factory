# v0.6 Plan — Laya Decision-Model Integration

Design source: this document. Target release: v0.6. Status: SHIPPED
(L1–L6 implemented 2026-10-14; `LAYA_MODE` default **off** — behavior
is byte-identical to v0.5.3 until the user enables shadow/on. The
2026-10-14 probe findings in §2 were captured before implementation
and drove the client design). The local service is documented in the
operator notes (`~/.venvs/laya`, launchd `com.local.laya`, 127.0.0.1:8019).

## 1. Summary

Laya (Convai Innovations, Apache-2.0) is a non-autoregressive
decision model: bidirectional encoders (ModernBERT-large English /
mmBERT-base multilingual, ~320-420M params) that return **bounded
decisions — `choice`, `score`, `noul` — with probabilities** over a
free-form state string. It is NOT a chat model and must never be
configured as a `Provider` in `@video/llm`.

This plan wires Laya into the pipeline as an **advisory decision layer**:
it answers the bounded questions the pipeline currently answers by
burning cloud tokens (per-scene motion refinement) or by regex
fall-through (visual component selection), and annotates the surfaces a
human reads (QA report). Three rules govern every integration:

1. **Advisory only.** Laya never replaces a human gate (plan §4:
   "Human approval is workflow state") and never drives a workflow state
   transition.
2. **Degrade to current behavior.** Every Laya call can fail, hang, or
   answer with low confidence. The caller falls back to exactly today's
   code path. `laya Decide()` never throws.
3. **Shadow first.** Each decision surface ships in `shadow` mode (log
   both answers, act on none) and is promoted to `on` only after the
   evaluation gates in §7 pass.

## 2. Ground truth — service measured 2026-10-14

Probed live against `http://127.0.0.1:8019` (`laya-0.3.21`, CPU,
preloaded). Client design must encode these facts:

| Fact | Value | Design consequence |
|---|---|---|
| `GET /health` | `{status, loaded, revisions, device, checkpoint_devices, cpu_fallbacks}` | pre-flight check, same pattern as flux `preflightAndSpawn()` |
| `POST /v1/systemone` | `{state, questions: {<qid>: {type, instructions, criteria?}}}` | `questions` is an OBJECT keyed by id; field is `instructions` (not `prompt`); `criteria` = option list |
| Answer shape | `{answers: {<qid>: {type, choice\|score\|noul, probabilities, confidence, answer_confidence, action:{act_probability}}}}` + `usage.input_tokens` + `routing.model/detection` | act on `choice`/`score`; log `routing.model` (english vs multilingual) for zh/en corpora |
| Wire limits | `state ≤ 50000` chars, ≤ 64 questions, ≤ 100 choice options, ≤ 32 score levels, ≤ 512 total options | per-scene states fit easily; batching questions into ONE call per scene is free |
| Latency (CPU) | warm ≈ 0.5 s/call; first call after service start > 15 s (observed timeout at 15 s) | client timeout 3 s after a healthy pre-flight; pre-flight itself allows 20 s; cold start never blocks a render because degrade-to-null |
| Concurrency | single inference worker (executor `max_workers=1`); overload → `503` + `Retry-After: 1` | client concurrency cap = 1-2, honor Retry-After once; 23 scenes ≈ 12 s serialized — still cheaper than 23 cloud calls |
| Auth | optional bearer (none configured; localhost-only) | send `Authorization: Bearer $LAYA_BEARER` only when env set |
| Calibration | probe: triage choice returned `confidence 0.0075`, near-uniform probabilities (0.37/0.28/0.35) — matches the known english-checkpoint temperature bug (operator notes) | `LAYA_MIN_CONFIDENCE` gate is MANDATORY; below threshold → treat as "no decision" |

Routing note: state text is auto-routed by script detection — Latin →
`english` checkpoint, CJK → `multilingual` (mmBERT). The pipeline's
zh-CN projects (e.g. hongmenyan) exercise the multilingual path; golden
sets must include zh scenes (§7).

## 3. What Laya is NOT (rejected integrations)

| Rejected | Why |
|---|---|
| A `Provider` / chat role in `ProviderConfig` | not generative; `ChatRequest/ChatResponse` cannot express bounded decisions; provider fallback machinery would silently "downgrade" quality roles to a 421M encoder |
| Article quality-gate judge replacement | the judge decides regeneration (cost lever, `article-review.ts`), so judge quality is load-bearing; a 421M encoder scoring `attractive/interesting/useful` over a 12k-char zh article is a quality gamble. Revisit ONLY as D5 shadow data (§5) |
| Workflow state-machine transitions | the 10-state machine is deterministic and replay-verified (11/11 replay, illegal-transition guard); ML confidence inside transitions breaks determinism and the replay contract |
| Replacing `planSceneMotion` heuristics | heuristics are pure, free, and instant; Laya adds nothing where the answer is already deterministic |

## 4. Architecture

```text
                    ┌────────────────────────── @video/llm ──────────────────┐
                    │  laya.ts — LayaClient (decide/health, never throws)    │
                    │  resolveLayaMode(): off | shadow | on                  │
                    └───────────────┬────────────────────────────────────────┘
             mode + client          │  advisory answers (or null)
        ┌───────────────┬───────────┴──────────┬──────────────────┐
        ▼               ▼                      ▼                  ▼
  D1 motion       D2 visual-classifier   D3 qa triage       D4 cli verbs
  pre-screen      fall-through assist    (advisory note     (command
  (skip cloud     (component choice      in QA report       disambiguation)
  LLM per scene)  when regex misses)     + contact sheet)
        │               │                      │                  │
        └───────────────┴──────────┬───────────┴──────────────────┘
                                   ▼
                 laya-decisions.jsonl (per project, append-only;
                 shadow rows carry `agreed: bool` for §7 scoring)
```

- **Client lives in `@video/llm`** (`packages/llm/src/laya.ts`) next to
  the providers it advises — one dependency edge, all packages already
  import `@video/llm`.
- **One JSONL sidecar per project** (`laya-decisions.jsonl`, appended
  under the project dir next to `article-review.yaml`): every decision
  records `{ts, surface, mode, state_sha256, questions, answers,
  routing_model, latency_ms, acted}`. Shadow rows add the deterministic/
  cloud answer and `agreed`. This is the §7 evaluation corpus and the
  audit trail ("Git remembers").
- **Pre-flight**: first client use per process calls `/health` (20 s
  budget, result memoized like flux `healthChecked`). Unhealthy → mode
  downgrades to `off` for the process, one stderr line, pipeline
  continues.

### Config surface

```yaml
# llm.config.yaml (optional, merged over env)
laya:
  mode: shadow        # off | shadow | on   (env LAYA_MODE; default off)
  url: http://127.0.0.1:8019      # env LAYA_URL
  min_confidence: 0.6             # env LAYA_MIN_CONFIDENCE
  timeout_ms: 3000                # env LAYA_TIMEOUT_MS
  bearer: null                    # env LAYA_BEARER
```

Default `off`. After D1-D3 pass their §7 gates, the default flips to
`on` in a later release — the same flip pattern flux used in v0.5.3.

## 5. Integration points (ranked)

### D1 — Motion pre-screen (highest value: cloud-call savings)

`video motion` today runs `planSceneMotion` (free baseline) then
`callMotionAgent` (cloud) for EVERY scene (`packages/cli/src/
motion-command.ts:176-211`). Laya pre-screens each scene:

- state: scene id, component, duration, beats, narration excerpt
  (≤ 600 chars), 1-line baseline spec summary
- question `needs_llm` (choice): `baseline_ok | refine`
- `on` mode: `baseline_ok` skips the cloud call entirely;
  `refine` behaves exactly as today. Skips are printed and counted.
- shadow mode: cloud call still runs; log whether laya would have
  skipped and whether the agent spec differed materially from baseline
  (spec JSON hash inequality — a cheap material proxy).

Expected yield: if laya routes even half the scenes to `baseline_ok`,
`video motion` drops from 23 cloud calls to ~12 (hongmenyan-scale
project). Cost per scene: one 0.5 s local call.

### D2 — Visual-classifier fall-through assist

`visual-classifier.ts` maps `visual:` keywords → component via regex
and falls through to `AnimatedIllustration` when nothing matches. In
`on` mode, ONLY the fall-through branch consults Laya (choice over the
17 registry component names, state = the scene's `visual:` text +
narration excerpt). Matched rules stay pure regex — determinism
preserved where it exists today. Component names are validated against
the REGISTRY before use; unknown → fall through as today.

### D3 — QA triage annotation (advisory; never a gate)

`@video/qa` render reports + contact sheets are read by humans at the
review gate. Laya gets the report summary (black frames, audio drift,
duration deltas, asset misses — all already computed) as state and
returns `pass | review | block` + one-line reason. The result is
written as an `advisory.laya` object in `qa/render-report.json` and a
small caption line on the contact sheet. The export gate logic itself
is UNCHANGED — this is a "where should I look first" hint. In `shadow`
mode, log agreement against the deterministic gate verdict.

### D4 — CLI verb disambiguation (tiny, optional)

Unknown/abbreviated `video <verb>` → single Laya choice over the verb
list instead of a bare "unknown command" (fit-assessment idea). Lowest
value; ship last, behind the same mode flag.

### D5 — (stretch) Judge shadow corpus

Not a mode, just reuse: feed `scoreArticle` prompts' axes as three
`score` questions with the article's first 2000 chars as state,
alongside the real cloud judge, and log agreement. Only decides
whether §3's judge rejection should be revisited. No behavior change
ever ships from D5.

## 6. Client contract (`packages/llm/src/laya.ts`)

```ts
export interface LayaQuestion {
  type: "choice" | "score" | "noul";
  instructions: string;
  criteria?: string[];              // choice options / score levels
}
export interface LayaAnswer {
  type: "choice" | "score" | "noul";
  value?: string;                   // choice | noul
  score?: number;
  confidence: number;               // as reported; gate before acting
  probabilities?: Record<string, number>;
  routingModel: string;             // english | multilingual | typed-decisions
}
export interface LayaDecision {
  answers: Record<string, LayaAnswer>;
  latencyMs: number;
}
export class LayaClient {
  constructor(opts?: { url?: string; timeoutMs?: number;
                       minConfidence?: number; bearer?: string });
  healthy(): Promise<boolean>;      // memoized /health, 20 s budget
  decide(state: string, questions: Record<string, LayaQuestion>):
    Promise<LayaDecision | null>;   // null = off/unhealthy/timeout/503
                                    // twice/low confidence — NEVER throws
}
```

Rules: `decide` retries a 503 once after `Retry-After`; answers below
`minConfidence` are dropped (absent from `answers`); every exit path
either returns a decision or `null` — callers write
`const d = await laya.decide(...); if (!d) { /* today's path */ }`.
Unit tests mock `fetch`; no test touches the live service (CI has none).

## 7. Shadow evaluation and promotion gates

Golden sets are built FROM `laya-decisions.jsonl` shadow rows plus the
hongmenyan run corpus (zh-CN — exercises the multilingual checkpoint).

| Surface | Metric (on golden set) | Promote `shadow → on` when |
|---|---|---|
| D1 motion | material-difference proxy: hash(agent spec, baseline) on laya-skip set | ≥ 90% of laya-skipped scenes have baseline == agent spec (i.e. the cloud call was wasted) AND ≤ 5% of `refine` scenes were baseline-identical |
| D2 classifier | agreement vs human-labeled component on 50 scenes (≥ 25 zh) | ≥ 85% overall AND ≥ 80% on zh |
| D3 triage | agreement vs deterministic QA gate verdict on ≥ 10 historical runs | ≥ 95% on pass/block; `review` disagreements only ever over-flag |
| Calibration | mean `answer_confidence` of acting decisions vs observed correctness | monotone-ish (higher-confidence bucket → higher agreement); else raise `min_confidence` and re-gate |

Each gate is re-runnable via `video laya eval <surface>` (T2), which
scores the JSONL corpus and prints the table row. A failed gate keeps
the surface in `shadow`; no silent promotions.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Uncalibrated confidence (measured: 0.0075 on probe) | mandatory `min_confidence` gate; calibration check is part of every promotion gate; track the upstream temperature fix (`laya-upstream` notes) and re-gate after upgrading `laya[serve]` |
| Laya service down / laptop CPU busy | degrade-to-null on every path; `off`-mode behavior is byte-identical to today; no pipeline step requires laya |
| zh-CN quality unknown on mmBERT path | golden sets are ≥ 50% zh (hongmenyan corpus); per-language promotion numbers in §7 |
| Serial inference adds latency to 23-scene renders | ~12 s worst case vs minutes of cloud calls saved; client caps concurrency at 2 and honors Retry-After |
| Drift between laya server and client assumptions (wire schema) | L2 `video laya health` prints the live schema facts (loaded checkpoints, revisions); client fails closed, never open |
